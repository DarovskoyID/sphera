# Лаборатория консенсуса mesh

Четыре отдельных процесса CometBFT v0.38.26 с равным весом голосов и разными
ключами. Это фиксированный лабораторный genesis: публичное вступление,
смена комитета и защита от Sybil ещё не реализованы. Валидаторы — роль будущих
логических серверов хранения, отдельная платная подписка им не требуется.

Из корня проекта (Python с установленной cryptography):

```sh
cd mesh-consensus
go test ./...
go build -o ../output/mesh-consensus-lab .
cd ..
python scripts/test-mesh-consensus.py ./output/mesh-consensus-lab
```

На Windows используйте имя `mesh-consensus.exe`. Тест создаёт временный стенд,
запускает четыре процесса и завершает их при любом исходе. Все RPC/P2P-адреса
только 127.0.0.1, прокси отключены. Порты выбираются ОС; редкая гонка за порт
завершает тест ошибкой. Существующий каталог лаборатории не перезаписывается.
Нет подключения к публичным пирами или изменения данных текущего мессенджера.

ABCI-приложение принимает существующий ASCII-формат подписанной владельцем
записи аккаунта. Проверяет подпись, сеть, self-certifying user_id, версию и
previous; конфликт отвергается детерминированно. FinalizeBlock готовит состояние,
Commit атомарно сохраняет его через LevelDB SetSync. Запросы видят только
committed-состояние; Info позволяет движку восстановиться и повторить блоки.
Идентичная текущая запись идемпотентна, исторические версии не откатывают head.

Проверяется доставка через реальный RPC, согласование четырьмя процессами,
работа при одном отключённом валидаторе, остановка подтверждений при двух,
возобновление/догон отставших, запрет конфликтующей версии и полный перезапуск.
Принятие в mempool не выдаётся за подтверждение. Тест не моделирует все виды
злонамеренного поведения и не заменяет аудит движка/интеграции.

Проверяемый мост: /snapshot возвращает committed-состояние (до 1 МиБ).
`--verify-genesis <локальный genesis>` проверяет доказательство из stdin:
`{state, signed_header}`. Используются официальные ValidateBasic/VerifyCommit,
публичные ключи и равные веса из локального genesis. Заголовок H+1 должен
подтверждать app hash состояния H, оба validator hashes закреплены. Заголовки
старше 30 сек или более чем на 5 сек из будущего отвергаются. Нужны часы с
допустимым расхождением. Проверяющий процесс не получает закрытых ключей.

Python ConsensusDirectory запрашивает снимок и соответствующий commit через
loopback RPC, вызывает проверку, сохраняет доказательство и высоту, запрещает
откат/смену genesis. MeshAuth использует этот каталог для лабораторного входа
без fixture read lease. При устаревании снимка доступ приостанавливается, сеанс
не отзывается. ConsensusUpdater автоматически обновляет каталог с ограниченной
частотой; старые данные не выдаются за текущее состояние. Пример отдельного
локального запуска рядом с уже работающим стендом (повторите --rpc для других
явно известных loopback-источников):

```sh
python scripts/mesh-directory-watch.py --binary output/mesh-consensus-lab --genesis /path/to/lab/0/config/genesis.json --state /path/to/directory.sqlite --rpc http://127.0.0.1:26657
```

Укажите фактический RPC-порт из lab.json. Этот процесс обновляет свою SQLite-базу,
не запускает сервер авторизации. Встраиваемый MeshAuth должен использовать тот
же объект ConsensusDirectory с ConsensusUpdater. Перед закрытием базы вызовите
updater.stop(). Фоновое обновление не подключается к обычному сайту автоматически.

Несколько процессов на одной машине могут использовать один файл SQLite:
один выполняет RPC, резервные читают и проверяют общий снимок. Системная
блокировка `<database>.refresh.lock` освобождается при завершении процесса;
резервный получает роль на следующем проходе. Не удаляйте этот файл при работе
стенда. В статусе есть role и cache_reads; attempts учитывает сетевые попытки.
Требуется локальный диск: NFS и совместная база между машинами не поддерживаются.

Границы: состояние и хеш пока пересчитываются целиком, каталог ограничен
памятью лаборатории; нет Merkle-доказательств ответа /account и браузерной
проверки финальности. Запрос с prove=true отвергается. RPC-ответ /account
сам по себе не доказательство финальности для недоверенного клиента.
Старые тестовые сертификаты sfera_mesh и read lease НЕ являются сертификатами
CometBFT и не создаются этим приложением. Публичный mesh, продуктовый вход,
автоматический ремонт троек, DHT и коммерческие разрешения пока не подключены.
Проверка поддерживает только неизменяемый лабораторный genesis; смена состава
и весов явно отвергается. Это не универсальный light client открытой сети.

Протокол ABCI: https://github.com/cometbft/cometbft/blob/v0.38.26/spec/abci/abci%2B%2B_app_requirements.md

Составы троек передаются отдельными каноническими транзакциями V2:
`{body: {domain, network, cluster, epoch, previous, members, licenses_hash}, consents, licenses}`.
domain — sfera-mesh-placement-v2, members — три отсортированных node_id,
consents — соответствующие публичные ключи и подписи тела всеми тремя узлами.
В record также входят три licenses существующего формата sfera-mesh-license-v1,
а body.licenses_hash связывает согласия с их SHA-256. Они проверяются каждым
валидатором по времени блока и закреплённым ключам компании. V1 читается как
прежняя история, но не принимается для новых переходов.
Начальный cluster = SHA-256 канонического `{domain: sfera-mesh-cluster-v1,
network, members}`. Новая эпоха заменяет ровно одного участника; два оставшихся
и новый участник дают согласие. Максимум два членства проверяется в общем
согласованном состоянии. Состав не является автоматически выбранным комитетом.

Снимок содержит placements и placement_history. Это позволяет журналу догонять
пропуски; старые account-only снимки без этих полей сохраняют прежний app hash.
История ограничена общим пределом лабораторного снимка, полноценного архивного
light client / компактного доказательства для огромного графа пока нет.

Python ReplicaJournal с require_consensus=True применяет подтверждённый состав
через apply_confirmed_placement и проверяет коммерческие/ресурсные правила.
Валидаторы проверяют согласия, последовательность и коммерческие подписи.
Ресурсные ограничения, зоны отказа и выбор лучшего кандидата пока проверяет
адаптер. Не используйте fixture с тестовыми ключами как сервис подписания.

Для НОВОГО стенда передайте --init --license-issuers /path/to/issuer-public.json.
Файл — объект issuer_id → public_key_hex; issuer_id = SHA-256 32 байт ключа.
В genesis записываются только эти публичные ключи. Без них лаборатория аккаунтов
работает, но новые составы отвергаются. Существующую сеть нельзя перенастроить
этим флагом. Верификатор сверяет ключи со своим локальным genesis, а не с пирами.
Пустые оплаченные modules допустимы; подпись профиля не разрешает операции модулей.
Исторические profiles проверяются на accepted_at и не истекают задним числом.

Локальное наблюдение за узлами: scripts/mesh-health-watch.py принимает --identity
(ключ узла), --roster (явный JSON с network и nodes), --state и --replays
(отдельные SQLite-файлы). Формат nodes: объект node_id → {public_key, endpoint},
где public_key — 32 байта hex, endpoint — закреплённый loopback URL.
Probe проверяет только доступность контрольного процесса. Наблюдатель не подписывает
составы автоматически и не выдаёт права на замену; для неё нужен прежний протокол
трёх согласий и консенсус. При завершении сначала остановите HealthMonitor,
затем закройте HealthJournal. Старые наблюдения не сохраняют статус healthy.
