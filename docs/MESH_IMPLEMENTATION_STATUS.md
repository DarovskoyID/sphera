# Mesh: состояние реализации

19 октября 2026 года. Требования: [архитектура](MESH_NETWORK_ARCHITECTURE_RU.md).

## Текущее состояние

| Область | Состояние |
| --- | --- |
| Публичный mesh runtime | Не включён; обычный мессенджер остаётся вне mesh |
| История, Merkle, репликация шифротекста | Подтверждённые эпохи и подписи компании проверяет консенсус; выбор лучшего кандидата и ресурсы пока проверяет адаптер |
| Коммерческий профиль узла | Подписанный API развёрнут; серверный smoke подтверждает подпись, отзыв и привязку |
| Каталог аккаунтов | В лаборатории проверяет снимок по app hash и подписям закреплённых валидаторов; глобального обнаружения нет |
| Вход по ключу | Лабораторные сеансы используют проверенное состояние живого консенсуса; UI, Django/JWT и WebSocket не подключены |
| Консенсус | Четыре процесса CometBFT и проверяемый мост к каталогу/входу; смена комитетов ещё не реализована |
| Открытое вступление/защита от Sybil | Не реализовано |

Ниже сохранена история слоёв реализации и их границ. Наличие библиотек и лабораторного входа не означает готовность публичной mesh-сети.

## Тринадцатый слой: коммерческие подписи на каждом валидаторе

Новые составы используют sfera-mesh-placement-v2: три коммерческих профиля входят
в запись, а их общий хеш — в тело, подписываемое всеми участниками. Нельзя заменить
список оплаченных модулей после получения согласий. Публичные ключи компании
закрепляются в app_state нового лабораторного genesis (--license-issuers); ID
издателя равен SHA-256 его Ed25519 public key. Валидаторы не получают закрытый
ключ компании, не выводят его из ключа узла и не принимают ключ издателя из
предложения. Без закреплённого издателя новые составы не принимаются. Смена
издателя через запуск существующего узла или изменение сохранённой БД запрещена.

Каждый валидатор проверяет подпись компании, сеть, node_id, канонический UUID
логического сервера, уникальность трёх серверных instance_id, список 15 модулей,
дубли модулей и сроки. Пустой список модулей допустим: размещение сообщений
бесплатного ядра не требует покупки модуля. Профиль действует не более 300 сек,
каждый срок оплаченного модуля должен покрывать срок профиля. Срок проверяется
по согласованному времени блока, а не локальным часам валидатора и не HTTP-запросом
к компании во время раунда. CheckTx предварительно проверяет последнее время
состояния; FinalizeBlock проверяет заново по времени финализируемого блока.

История хранит accepted_at: при проверке старого снимка профиль проверяется на
момент принятия. Истечение его срока позже не удаляет состав, сообщения или
возможность прочитать архив. Для нового перехода нужен новый действующий профиль.
V1 остаётся читаемым форматом прежней лабораторной истории; новый переход без
V2 и подписи закреплённой компании отклоняется. Закрепление ключей в новой сети
не является скрытой миграцией существующего публичного узла — mesh пока выключен.

Сквозной тест подписывает профили отдельным тестовым издателем и проверяет их
Go/Python-кодом. Четыре живых валидатора отвергают подмену модулей, просрочку,
будущее время выпуска, слишком долгий TTL, неизвестного издателя, неверный узел/
сеть, неизвестный модуль и повтор instance_id. Затем принимают правильный состав,
восстанавливают данные на семи HTTP-узлах и догоняют историю. В тесте закрытый
ключ издателя остаётся в памяти отдельной тестовой оснастки, в genesis только
публичный ключ. Производственный закрытый ключ коммерческого сервиса не читается.

Границы: ресурсная ёмкость, независимость физических зон отказа и лучший кандидат
среди явно переданного пула пока проверяются адаптером размещения, не контрактом
консенсуса. Нет полного глобального каталога кандидатов, протокола смены издателя,
admission/Sybil и автоматического контроллера перестройки. Отзыв уже выданного
профиля ограничен его коротким сроком; платные операции по-прежнему проверяются
прежним коммерческим API, профиль размещения их не разрешает и не даёт голосов.
Публичный mesh остаётся выключенным.

## Двенадцатый слой: устойчивые наблюдения о доступности

HealthJournal отправляет закреплённому узлу подписанный probe с новым challenge.
Ответ подписан самим узлом и связан с nonce запроса, адресатом, сетью, операцией
и challenge. Неверная подпись, другой адресат или другой challenge не считаются
успехом. Проверка показывает доступность контрольного HTTP-процесса, а не
исправность диска, наличие всех сообщений или ресурсную ёмкость сервера.

По умолчанию узел становится unreachable только после трёх последовательных
неудач и окна не менее 10 сек. Один сбой даёт suspect; для healthy нужны два
последовательных успеха. Начальное состояние и устаревшие наблюдения — unknown.
После большого перерыва последовательности наблюдений начинаются заново.
Счётчики, последняя проверка и next_probe сохраняются в SQLite FULL. Следующий
интервал резервируется до сетевого запроса: перезапуск не создаёт цикл частых
запросов. Смена наблюдателя/сети/закреплённого набора или политики не сбрасывает
эту базу молча. Перевод часов назад отвергается, а не превращается в успех.

HealthMonitor выполняет ограниченные пакеты с паузами, поддерживает остановку
и не даёт закрыть журнал во время работы. Локальная системная блокировка и
сохранённое расписание координируют несколько процессов с одной базой. Клиент
транспорта имеет общий срок чтения ответа и ограничение размера. Для отдельного
локального запуска есть scripts/mesh-health-watch.py; адреса только loopback,
ключ наблюдателя — ключ узла, а не пользовательский архивный корень.

advisory привязывает наблюдения к свежей подтверждённой эпохе кластера. Если
ровно один участник локально unreachable, а два других healthy, можно начать
сбор согласий; replacement_authorised всегда false. Само наблюдение не меняет
состав и не запускает копирование. Проверка согласий, кворум CometBFT и локальная
коммерческая политика предыдущего слоя остаются обязательными. Сквозной тест
проверяет настоящий отказ HTTP-узла: эпоха остаётся прежней до отдельного
подписанного предложения, а после подтверждения восстанавливаются копии.

Границы: это взгляд одного наблюдателя, а не объективное доказательство отказа
или BFT-сертификат. Сетевая перегородка может выглядеть как отказ. Нет объединения
независимых наблюдений, сетевого сбора согласий и автоматического контроллера
замены. Коммерческие подписи всё ещё проверяются адаптером, не каждым валидатором.
Публичный mesh и автоматическое подключение сервера по-прежнему выключены.

## Одиннадцатый слой: подтверждённые эпохи состава троек

CometBFT теперь согласует записи sfera-mesh-placement-v1 отдельно от аккаунтов.
Начальный ID кластера выводится из сети и трёх ID участников. Каждая запись
содержит эпоху, хеш предыдущей записи и отсортированные ID трёх узлов; каждый
участник нового состава подписывает именно это тело своим Ed25519-ключом.
Подписи связываются с self-certifying node_id. Нет общего ключа генерации или
нового единоличного оператора подписания. В тестах ключи принадлежат стенду;
производственный сбор согласий через сеть пока не реализован.

Все валидаторы проверяют три согласия, сеть, начальную идентичность кластера,
последовательность эпох и previous, ровно одну замену участника и максимум два
одновременных членства узла. Повтор той же записи идемпотентен, другая запись
той же эпохи отклоняется. Снимок содержит подтверждённую историю составов;
Go/Python проверяют её непрерывность и соответствие текущему head. Проверка
снимка и его свежести остаётся привязана к подписям комитета и app hash.

ReplicaJournal(require_consensus=True) блокирует ручные составы до первого
подтверждения. Режим сохраняется и не отключается при повторном открытии с
обычными параметрами. apply_confirmed_placement принимает данные только из
ConsensusDirectory той же сети и закрепляет genesis. Перед применением заново
проверяются свежие коммерческие профили, зоны отказа, ёмкость, локально известные
членства и лучший кандидат в явно переданном пуле. Согласованный, но не прошедший
эту проверку план не применяется. После перехода в этот режим register_cluster /
replace_failed не позволяют обойти подтверждение; неподтверждённые кластеры
не принимают задания. Старые квитанции не подтверждают новую эпоху.

Журнал может догнать несколько пропущенных эпох по доказанной истории сразу
до последнего состава; промежуточные держатели сохраняются как источники данных.
Свежие профили проверяются для последнего перехода, а не выдаются за исторические
сведения об оплате. Сетевой тест объединяет четыре процесса консенсуса и семь
HTTP-хранилищ: начальный состав, согласованная замена, восстановление блока,
отказ конфликтующему плану, перезапуск и догон журнала с эпохи 1 до 3.

Границы: коммерческие подписи и правила выбора кандидата ещё не исполняются
каждым BFT-валидатором — консенсус фиксирует согласованную участниками запись,
а право применить её проверяет адаптер. Это не завершённое публичное управление
размещением. Нет сетевого сбора согласий, автоматического детектора отказов,
открытого admission/Sybil, смены комитета и глобального поиска кандидатов.
История пока входит целиком в ограниченный лабораторный снимок 1 МиБ; для большого
графа нужны компактные доказательства и внешние подтверждённые индексы. Согласие
на хранение не даёт подписку, право голоса или перенос пользователя на другой
entry point. Публичный mesh по-прежнему выключен.

## Десятый слой: устойчивое копирование и восстановление троек

ReplicaJournal сохраняет шифротекст, очередь заданий, эпоху состава тройки,
проверенные копии и задержку повторов в SQLite FULL. Повторная постановка
идемпотентна; перезапуск не теряет прогресс и не отменяет паузу при ошибке.
Один локальный журнал выполняет один пакет копирования за раз; пакет ограничен
64 заданиями, блок — 256 КиБ, явно закреплённый список соседей — 64 узлами.
После put выполняется get с проверкой подписи узла, контекста запроса и хеша.
Только три проверенные копии текущей эпохи дают статус replicated. Этот статус
не является consensus commit, доказательством постоянного хранения или текущей
доступности узла: время проверки каждой копии сохранено отдельно.

По явному сообщению оператора об отказе строится новая тройка из двух оставшихся
и подходящего кандидата: сохраняются проверки свежего коммерческого профиля,
зон отказа, ёмкости, близости количества/набора оплаченных модулей и максимум
двух членств в локально известном графе. Сначала может быть временно заимствован
узел соседней тройки; при появлении свободного узла оператор может заменить
временного участника и вернуть его к одному членству. Версия плана проверяется
атомарно; квитанции предыдущей эпохи не завершают новое задание даже при смене
плана во время копирования. Старые копии не удаляются автоматически.

Если локальный шифротекст отсутствует/повреждён, восстановление ищет его у
текущих и прежних известных держателей, проверяя ожидаемый хеш. Недоступный
источник отличается от ответов not_found всех известных держателей. Ни один
из этих результатов не объявляется безусловной окончательной потерей во всей
сети; задание остаётся незавершённым. Хеш не используется для генерации утраченных
данных. Отсутствие всех копий не даёт статус replicated.
Корректный put с уже проверенным content hash может исправить повреждённые
байты на реплике: другое содержимое под тем же адресом не принимается. Подписанный
ответ с неправильным шифротекстом не засчитывается, даже если отправитель известен.

Storage.affected_page использует индекс (cluster_id, dialog, position) и seek
курсор: enqueue_manifest ставит только ограниченную страницу затронутых блоков,
не проходит диалог от начала до конца. Независимый манифест позволяет поставить
задание по ожидаемому хешу даже при потере локальных байтов. Проверены страницы,
перезапуск, восстановление с реплик, временный/постоянный сосед, повреждение копии,
исчезновение всех известных байтов, недоступный источник и конфликт эпох.
restore_manifest_page возвращает восстановленные байты в локальное Storage,
повторно сверяя хеш и число шифротекстов с независимым манифестом. При этом
двунаправленные связи и прежний Merkle checkpoint не изменяются.

Границы: планы состава пока задаёт лабораторный оператор, а не BFT; журнал —
локальный координатор, не глобальный каталог размещения. Candidate.grant_verified
должен приходить из проверенного коммерческого профиля, в стенде используются
явные тестовые профили. Автоматические детекторы отказов, согласование размещения,
распределённый ремонт и подключение сообщений продукта ещё не реализованы.
Нет GC старых копий. Права модулей и выбранный пользователем entry point не
меняются. При полной утрате манифеста потребуется внешняя подтверждённая копия
метаданных; начало/конец цепочки без неё не восстанавливают потерянные сообщения.

## Девятый слой: один обновляющий процесс для общей локальной базы

Процессы с одной SQLite-базой теперь выбирают единственного сетевого обновляющего
через системную файловую блокировку рядом с базой. Резервные процессы проверяют
сохранённое доказательство и читают общую базу, не запрашивая RPC. Статус явно
показывает роль leader/follower, число сетевых попыток и чтений общего снимка.
После штатной остановки или принудительного завершения ведущего другой процесс
получает блокировку и продолжает обновление; истечение самодельной lease не
используется. Файл блокировки не удаляется, чтобы не создать два разных inode
с двумя владельцами. Привязка базы к genesis при конкурентном открытии атомарна.

Есть проверки на Windows и в Linux CI: запрет второго владельца в отдельном
процессе, освобождение после kill и ошибки файловой системы. Сквозной тест
запускает два отдельных Python-процесса на живом CometBFT, проверяет ноль сетевых
попыток у резервного, принудительно завершает ведущего и ждёт продвижения
подтверждённой высоты через новый процесс. Права на модули и entry point не меняются.

Это механизм для локального диска одной машины. SQLite/файл блокировки на NFS,
общая папка между машинами и распределённая координация не поддерживаются.
Для логического сервера из нескольких машин ещё нужны общее хранилище и
межмашинная координация с fencing; публичный mesh остаётся выключенным.

## Восьмой слой: автоматическое обновление подтверждённого каталога

ConsensusUpdater обслуживает один объект каталога одним фоновым потоком. Использует
только явно заданные loopback-источники (до 16), сохраняет выбранный доступный
источник, при ошибке пробует следующий. Это смена источника подписанных
метаданных, а не entry point пользователя; сервер сеанса и коммерческие
разрешения не меняются. Ключи доверия берутся из прежнего локального genesis.

Нормальный интервал — 5 сек; ошибки увеличивают паузу до 20 сек, с разбросом
для распределения нагрузки. Нельзя настроить интервал меньше 2 сек. Запросы
входа/чтения и проверка статуса не запускают дополнительные обновления.
RPC имеет ограничения размера, времени чтения и поддерживает остановку;
ожидание следующего подписанного блока ограничено и отменяемо. Медленная
проверка нового снимка не держит блокировку чтения свежего кэша. Подпись,
свежесть, защита от отката и семантика 503 без отзыва сеанса сохранены.

При запуске сохранённый снимок проверяется заново. Просроченный снимок не
становится готовым только из-за перезапуска. Остановка прерывает паузу; закрыть
каталог до завершения обновления нельзя. Статус содержит счётчики и категории
ошибок без записей аккаунтов, ключей и токенов. Есть отдельный локальный запуск
scripts/mesh-directory-watch.py; автоматической регистрации публичного узла нет.
Межпроцессный выбор единственного обновляющего сервиса пока не реализован:
несколько процессов с отдельными объектами каталога не координируют расписание.

Сетевой стенд проверяет недоступный первый источник, получение подтверждений
от другого, автоматическое продвижение каталога после восстановления кворума
и запрет двух обновляющих потоков. Отдельные тесты проверяют отсутствие цикла
частых запросов, остановку во время паузы и доступность чтения при проверке.
До продуктового mesh остаются распределённый каталог и компактные доказательства,
публичный допуск/смена комитета, роли троек хранения и интеграция интерфейса/ACL/2FA.

## Седьмой слой: проверяемый мост консенсуса к каталогу и входу

Приложение отдаёт ограниченный 1 МиБ снимок committed-состояния. Отдельный
проверяющий процесс CometBFT получает снимок и signed header, но доверяет только
локально закреплённому genesis с четырьмя равновесными валидаторами. Проверяются
сеть, структура заголовка, совпадение validator hashes, подписи более 2/3 голосов,
app hash и точная связь: заголовок H+1 подтверждает состояние высоты H. Ключи
валидаторов не передаются проверяющему процессу или Python-каталогу. Даже новая
правильная подпись владельца не позволяет подменить запись внутри снимка.

ConsensusDirectory сохраняет доказательство и максимальную проверенную высоту
в SQLite, запрещает откат и конфликт на той же высоте после перезапуска. Genesis
нельзя молча сменить. Каждый account дополнительно проверяется Python-кодом.
Это целый заверенный снимок, а не Merkle-доказательство отдельного /account.
Доверять одному RPC-ответу /account по-прежнему нельзя.

MeshAuth умеет работать с этим каталогом без вручную подписанной read lease:
свежесть ограничена 30 секундами времени подписанного заголовка, допустимое
опережение часов — 5 сек. Обновление снимка выполняется явно; фонового сервиса
ещё нет. Снимок может отставать в пределах этого окна, мгновенную глобальную
актуальность оно не гарантирует. Просрочка блокирует доступ до обновления,
не отзывая токен; logout остаётся доступным. Смена версии аккаунта после выдачи
challenge блокирует завершение старого запроса. Старый формат account-confirm
и fixture read lease не принимаются в новом режиме.

Сквозной стенд проверяет эти свойства вместе с живыми четырьмя процессами,
потерей кворума и восстановлением. Остались смена комитета/публичный допуск,
масштабируемые доказательства, браузерная проверка финальности, автоматическое
обновление каталога и продуктовый вход с существующими ACL/2FA. Публичная сеть
по-прежнему отключена. Модель доверия фиксированного genesis не выдаётся за
универсальный light client динамической открытой сети.

## Шестой слой: живое согласование на четырёх валидаторах

Добавлена [лаборатория CometBFT](../mesh-consensus/README.md), закреплённая на
v0.38.26. Четыре отдельных процесса с разными ключами и одинаковым genesis
принимают подписанные владельцем записи аккаунта через ABCI. Проверки подписи,
сети, версии и previous выполняются независимо каждым валидатором. Нет выдачи
кворума одним координатором. Согласованные изменения сохраняются атомарно
только в Commit; запросы не видят незавершённое состояние FinalizeBlock.

Сквозной тест запускает настоящие loopback RPC/P2P-процессы, отключает одного,
затем второго валидатора, проверяет остановку подтверждений без кворума,
возобновление после возвращения третьего, догон четвёртого, отказ конфликтующей
версии и восстановление всех процессов с диска. Формат владельца дополнительно
проверяется Python-кодом существующего каталога. Этот тест добавлен в CI и
блокирует деплой при неуспехе.

Это отдельный лабораторный runtime: прежние Python-сертификаты/read lease ещё
не потребляют финальность CometBFT. Нет клиентского light client и доказательства
принадлежности /account к app hash; RPC-ответ нельзя считать таким доказательством.
Хеш/состояние пока пересчитываются целиком, без масштабируемого индекса. Роли
валидаторов в стенде не распределены по живым тройкам хранения. Не реализованы
публичный допуск, смена комитета, DHT и связка с UI/JWT. Mesh-инсталлятор остаётся
заблокированным до завершения этих частей. Следующий шаг — проверяемый мост
CometBFT commit → состояние каталога → свежесть входа.

## Реализован первый слой

- Отдельный Python-пакет sfera_mesh, не подменяющий текущий сервер mesh-сетью.
- Двунаправленные блоки шифротекста, защита от повторных ID в локальной модели, курсоры последних 100 сообщений.
- Дерево Merkle и проверка доказательств с контролем позиции, размера дерева, изменения содержимого и лишних элементов доказательства.
- Локальное устойчивое SQLite-хранилище блоков и отдельный индекс: двунаправленные связи, контрольные точки, индекс cluster → затронутые диапазоны, проверка шифротекста при чтении, сохранение метаданных после потери блока.
- Подбор троек по количеству оплаченных модулей, затем совпадению наборов; обязательная проверка разных зон отказа, ресурсов и отметки проверенной лицензии.
- Выбор временного соседа с ограничением двух кластеров. При одинаковой совместимости свободный сервер предпочтительнее уже занятого.
- Чистая функция доступа по разрешениям выбранного entry point. Действующие серверные проверки лицензий остаются в sfera_modules и не заменены доверенными флагами клиента.
- Linux install.sh с выбором corporate/personal/mesh, сохранением standalone-режима и запретом молчаливой смены. Mesh отклоняется до изменения файлов, пока нет сетевого runtime.
- Режим deployment.env подключается к создаваемым systemd-сервисам; прежние установки без настройки остаются personal, вне mesh.
- Проверки алгоритмов и изоляции установщика подключены к CI.

## Границы первого слоя

Это не готовая mesh-сеть. Первоначальный тест семи кандидатов проверяет подбор. Отдельный сетевой тест второго слоя теперь поднимает семь локальных HTTP-узлов, но ещё не моделирует BFT-консенсус. Хранилище не подтверждает распределённую запись. Узлы дерева сохраняются в SQLite и обновляются по пути добавленного блока; доказательство запрашивается по уровням без полного обхода истории. Полная функция leaves нужна только для диагностического сравнения с эталоном в тестах. Шифротекст поступает готовым: шифрование и проверка E2EE-происхождения ещё не интегрированы. Флаг grant_verified — внутренний вход алгоритма, не HTTP API и не замена проверки подписи коммерческого сервиса.

## Следующие обязательные части

1. Подписанные сетевые идентичности, admission и проверяемые подтверждения лицензий от коммерческого API.
2. Репликация и консенсус с durable quorum, learner-процедурой, сменой состава и fencing старых участников. Выбранная библиотека должна иметь проверенный протокол; локальная модель его не заменяет.
3. Распределённый каталог аккаунтов и размещения, внешние контрольные точки и индекс доступности.
4. Клиентское хранилище ключей Argon2id, протокол входа, E2EE диалогов/групп, восстановление и отзыв устройств.
5. Интеграция истории с действующим API и UI, ручной выбор entry point и объяснение недоступных модулей.
6. Сетевой стенд на семи изолированных узлах с отказами, затем реальный месячный стенд.
7. Включение рабочего mesh-режима установщика только после этих проверок.

Данные текущего сервера не мигрированы, шифрование не переключено, существующие аккаунты в mesh не опубликованы.


Уточнение доверия: участие операторов открыто для всех. Raft/обычное большинство тройки не выбраны как защита от злонамеренных серверов. Пользователь согласовал тройки хранения и роли валидаторов на тех же серверах. Комитет требует минимум четырёх node_id из разных троек; Sybil-защита не определена. Пока разрабатываются независимые от этого решения хранилище, индексы и политики размещения.


Дополнительно реализована проверка подписанных контрольных точек Ed25519: идентичность сети и комитета, версия, предыдущий хеш, порог более 2/3, отклонение повторных подписантов и изменённых данных. Локальный SQLite-журнал запрещает повторную подпись другого содержания на той же высоте даже после перезапуска. Это проверка сертификатов и защита от двойной подписи, а не готовый BFT-консенсус: раунды, блокировки, смена комитета, защита от отката доверенной конфигурации и Sybil остаются обязательными. Сертификат не может сам назначить собственный доверенный набор подписантов.


## Второй слой: идентичности, сетевой стенд и клиентский архив

Реализованы устойчивые Ed25519-идентичности узлов с запретом перезаписи ключа. Подписанный конверт связывает отправителя, адресата, сеть, операцию, время, nonce и содержимое. SQLite-журнал отклоняет повтор запроса после перезапуска; подписи ответов привязаны к nonce конкретного запроса. Сетевой код не наследует JWT_SECRET старых дополнительных узлов.

Добавлен настоящий HTTP-стенд на семи локальных слушателях 127.0.0.1. Узлы сохраняют шифротекст на диске, подтверждают подписанную квитанцию и проверяют хеш при чтении. Тест отключает один из трёх держателей, получает копию с живой реплики, передаёт её временной реплике и запасному узлу. Новая подпись позволяет безопасно повторить идентичную запись. Это проверка транспорта, а не автоматическая смена состава или BFT-консенсус. Квитанция stored означает локальную устойчивую запись, а не подтверждение всей сетью.

Транспорт намеренно слушает только loopback и использует явно заданный тестовый roster. Он не публикуется в nginx, не загружает адреса из чужих запросов и не открывает production mesh. Для внешней сети нужны TLS, admission, ограничения ресурсов, защита от Sybil и согласованный набор валидаторов.

В src/core/mesh/vault.ts добавлены клиентские функции случайного корневого ключа, оболочки Argon2id (64 MiB, 3 прохода, 1 полоса) + AES-256-GCM и отдельных архивных ключей HKDF с контекстом пользователя/диалога/сообщения. Профиль KDF фиксирован и проверяется до расчёта: удалённый узел не может подставить неограниченный объём памяти. Смена пароля обновляет оболочку, сохраняя корень и прежние сообщения. Корневой ключ и пароль не отправляются этими функциями в сеть и не сохраняются в localStorage.

Тесты проверяют вход на другом устройстве через передачу JSON-оболочки, неверный пароль, замену пользователя/диалога, повреждение шифротекста и смену пароля. Дополнительно проверяется открытый тестовый вектор, созданный независимой реализацией cryptography Argon2id/AESGCM. Это криптографические функции архива, пока не подключённые к действующему входу/переписке. Перед UI-интеграцией тяжёлый KDF следует вынести в worker и проверить бюджет памяти на Android. JS не гарантирует полное стирание всех копий секретов из памяти.

Для разблокировки архива новое устройство должно получить доверенную оболочку именно своего пользователя; сетевой каталог аккаунтов и аутентификация пока не реализованы. Архивный ключ не отдаётся собеседнику. Передача сообщений собеседникам, групповой E2EE-протокол, прямой секретности, восстановление и отзыв устройств ещё не реализованы.

Проверки:

```text
python -m unittest sfera_mesh.test_protocol sfera_mesh.test_certificates sfera_mesh.test_transport
node scripts/test-mesh-vault.cjs
```

Зависимость Argon2id: hash-wasm 4.12.0, зафиксирована в package-lock.json; описание API: https://github.com/Daninet/hash-wasm.


## Третий слой: подписанный коммерческий профиль узла

В приватном API добавлен POST /v1/mesh/attestation. Запрос требует действующий credential экземпляра и Ed25519-доказательство владения идентичностью узла. Экземпляр лицензии навсегда связывается с одним node_id и одной сетью; перенос на другой узел или сеть возвращает конфликт. Обратная уникальность не позволяет зарегистрировать один node_id под несколькими экземплярами. Восстановление потерянной идентичности потребует отдельной операторской процедуры; обычный вход пользователя на другой сервер эту привязку не меняет.

Ответ содержит подписанный публичный профиль: issuer, instance_id, node_id, network, время выпуска/окончания и действующие оплаченные модули. Максимальный срок — 5 минут, не дольше ближайшего окончания включённой подписки. Отзыв отражается в следующем запросе; уже выданный профиль сохраняет ограниченный срок. Поэтому профиль применяется только для размещения: платные действия продолжают проверяться прежним коммерческим API, профиль не является офлайн-лицензией операций или правом голоса валидатора.

На стороне ядра проверяются закреплённый публичный ключ issuer, подпись, формат, узел, сеть, экземпляр, время и модули. placement_candidate строится из проверенного профиля; подбор отвергает просроченные профили. Failure domain пока является входом политики, не доказанной физической независимостью; коммерческая подпись не решает Sybil и не подтверждает независимость владельцев.

Операторская команда mesh_license_profile запрашивает профиль через фиксированный коммерческий URL и существующий backend credential. Закрытый ключ узла, пароль пользователя, содержимое сообщений и ключ активации не передаются. Публичный ключ issuer задаётся явно; ответ сервера не может самостоятельно назначить новый доверенный ключ. Файл результата не перезаписывается. Команда не включает mesh, не меняет подписки и не переносит пользователя между entry point.

Узел с нулём оплаченных модулей может получить пустой подписанный профиль для уже существующего экземпляра. Публичная самостоятельная регистрация бесплатных mesh-узлов и её ограничения ещё не реализованы: нынешний credential выдаётся активацией или операторским issue_instance. Это не вводит плату за mesh-ядро.

Ключ подписи коммерческого сервиса создаётся один раз bootstrap_mesh_issuer в постоянном state-volume, с правами 0600, и не заменяется при повторном запуске. В stdout выводятся только issuer и публичный ключ для закрепления доверия. При утрате или смене ключа прежние verifier не начинают автоматически доверять новому. Команда smoke_mesh проверяет реальный loopback HTTP: подпись, набор модулей, отзыв и запрет переноса привязки; использует и удаляет только собственный одноразовый тестовый экземпляр.

Пример подготовки оператором (после развёртывания API и получения публичного issuer из доверенного канала):

```text
python manage.py mesh_identity --output /path/node.key
python manage.py mesh_license_profile --identity-file /path/node.key --network mesh-test --issuer-public-file /path/issuer-public.json --output /path/fresh-profile.json
```

Это слой лицензирования/размещения, а не завершённый admission, консенсус или сетевой вход пользователя.


Дополнительная сквозная проверка `scripts/test-mesh-license-integration.py` при наличии приватного checkout поднимает настоящий локальный HTTP API с отдельной БД в памяти и вызывает его клиентом ядра. Проверяет совместимость подписи между репозиториями, отзыв и запрет смены узла. Пользовательские БД и credentials не используются. Эта проверка запускается отдельно: публичный CI ядра не имеет доступа к приватному checkout.


## Четвёртый слой: реплицируемый каталог аккаунтов

Добавлен AccountDirectory: устойчивые подписанные владельцем записи аккаунта с self-certifying user_id (SHA-256 с отдельным доменом от Ed25519 public key), номером версии, хешем предыдущей записи и хешами зашифрованной оболочки корневого ключа/индекса диалогов. Новая версия принимается только после предыдущей; повтор той же записи идемпотентен, конфликт на той же версии не выбирается произвольно. Записи, ключи сети и закреплённого комитета сохраняются в SQLite и не меняют доверенную конфигурацию молча после перезапуска.

Поверх подписи владельца есть отдельный слой подтверждения: каталог принимает внешние сертификаты ранее закреплённого комитета, проверяет более 2/3 разных подписантов, последовательность высот и предыдущий хеш. Сохранённый подтверждённый head аккаунта не откатывается при повторном получении старого сертификата. Подпись владельца не называется подтверждением валидаторов. Каталог не создаёт сертификаты и не реализует раунды BFT; тестовые сертификаты подписываются явным набором лабораторных ключей.

Лабораторный HTTP-транспорт поддерживает account-put/get/confirm. Ответ confirmed содержит сам сертификат: клиент проверяет его своим закреплённым комитетом, а не доверяет флагу соседа. Корневые ключи и пароли в записи отсутствуют. Получение записи другим сервером не выдаёт пользовательский сеанс и не открывает платные модули.

Добавлены publish_account и resolve_account для ограниченного списка до 16 заранее известных соседей. Resolver запрашивает доступные копии, обнаруживает расхождения одинаковой версии, проверяет цепочку и не принимает ответ старее уже сохранённой версии. Синхронизация ограничена 64 версиями за вызов и явно сообщает, если нужно продолжение; без полного подтверждения цепочки не перескакивает сразу к большему счётчику. Запросы к репликам не меняют выбранный пользователем entry point. Это ещё не глобальный DHT/поиск всех узлов графа.

В клиенте account.ts добавлены создание Ed25519-идентичности, защита её 32-байтового seed оболочкой Argon2id, подпись/проверка записей, проверка хеша найденной оболочки и локальное открытие ключа на другом устройстве. Seed служит корнем: архивные ключи выводятся отдельным HKDF-контекстом, ключ не передаётся собеседникам. После смены пароля новая версия записи указывает на новую оболочку, идентичность и архивный корень сохраняются. Совместимость формата/подписи WebCrypto и Python проверяется открытым тестовым вектором.

Клиентские функции не обращаются к сети и не создают JWT. Пока они не подключены к текущим экранам регистрации и входа. Требуется проверить поддержку WebCrypto Ed25519 в целевых браузерах; отсутствие поддержки завершается ошибкой, не генерацией ключа на сервере. Модель ротации/восстановления идентичности и отзыва устройств ещё не реализована.

Сетевой тест на семи реальных локальных слушателях реплицирует запись, отключает исходный узел, разрешает аккаунт через другую реплику и получает новую версию от одного из оставшихся соседей. Проверяются неверные подписи, конфликты, откат, продолжение ограниченной синхронизации, сертификат с недостатком голосов, сертификат не того аккаунта и сохранение подтверждённой версии после перезапуска.

Важные границы: новый клиент без известной свежей контрольной точки не может доказать, что сеть не скрыла более новую запись. Валидный старый сертификат сам по себе не доказывает актуальность. Локальная защита от отката предполагает сохранность локального состояния; откат всей БД из старой копии требует сравнения с внешним доверенным checkpoint. Обнаружение вилки владельца не заменяет её разрешение BFT-протоколом. Подтверждение глобальных checkpoint импортируется отдельно от поиска владельческих записей. Глобальные логины/алиасы, распределённое обнаружение реплик, PAKE/сеансы входа, публичный admission/Sybil и полноценный консенсус остаются незавершёнными.


Сквозной сценарий scripts/test-mesh-account-integration.py подключён к CI: первый отдельный JS-процесс создаёт идентичность, зашифрованный архив и зашифрованный индекс, после чего завершается. Семь HTTP-узлов сохраняют и передают только подписанную запись и шифротекст; исходный держатель останавливается. Второй отдельный JS-процесс получает данные с реплики, проверяет подпись/хеши и открывает архив своим тестовым паролем. Корневой ключ не сериализуется в межпроцессные данные. Это не JWT-вход и не доказательство BFT-финальности; используются одноразовые тестовые данные и loopback roster.


## Пятый слой: вход по ключу на выбранном entry point

Добавлен MeshAuth для лабораторного сервера. Для выдачи запроса входа нужна подтверждённая запись аккаунта и подписанное более чем 2/3 закреплённых валидаторов разрешение чтения текущей контрольной точки (read lease), действующее максимум 60 секунд. Подпись владельца записи без сертификата и один флаг ready не разрешают вход. Lease проверяет сеть, состав комитета, высоту, хеш checkpoint, срок и уникальность подписантов. После изменения checkpoint старая lease не открывает доступ. Выдача таких разрешений живым BFT-сервисом ещё не реализована; в тестах они явно подписываются лабораторными ключами.

Сервер формирует подписанный одноразовый запрос, связывающий сеть, node_id выбранного entry point, user_id, точную версию/хеш аккаунта, случайный клиентский nonce и случайный challenge_id. Устройство сначала проверяет ключ сервера и контекст, затем подписывает запрос своим ключом локально. Пароль и корневой ключ не входят в HTTP-запросы. Повторная подпись не создаёт второй сеанс; использование того же запроса на другом entry point отклоняется. При изменении подтверждённой записи между началом и завершением вход нужно начать заново.

Успешный вход выдаёт непрозрачный случайный bearer-токен на 10 минут только для этого entry point. В SQLite хранится SHA-256 с отдельным доменом от токена, но не сам токен. Сеанс переживает перезапуск процесса с тем же ключом узла и БД. Повторное завершение одного challenge атомарно отклоняется, включая одновременные запросы. Есть лимиты числа незавершённых запросов и сохранённая защита от смены node_id/доверенного комитета поверх прежней БД.

Сеанс имеет scope mesh-identity: это не JWT существующего Django-приложения, не администраторские права, не подписка на модуль и не разрешение действовать на другом сервере. Выбор entry point не меняется автоматически. Токен не копируется между серверами. При проверке сеанса сервер заново проверяет готовность каталога. Временное отсутствие свежей lease возвращает HTTP 503 и не отзывает сеанс; после восстановления контроля сеанс может продолжить работу в пределах своего срока. Logout доступен даже при недоступном каталоге; отзыв сохраняется в БД.

Лабораторные маршруты /mesh-lab/auth/challenge, complete, session и logout доступны только на уже существующем loopback-стенде, не подключены к nginx или URL текущего сайта. Служебные ответы подписаны выбранным сервером и привязаны к nonce запроса. Клиент auth.ts проверяет подпись и закреплённый node public key, сеть, аккаунт, nonce, сроки, scope и идентификатор сеанса. Клиентские функции не выполняют редиректов, не записывают токены в localStorage и не отправляют пароль. Неверная подпись, подмена адресата, просроченный challenge и повторное использование proof проверены тестами.

Сквозной тест семи узлов теперь включает реальный HTTP-вход из отдельного JS-процесса после восстановления ключа с реплики: вход, проверка сеанса, запрет того же токена на другом готовом entry point, выход и отказ отозванного токена. В тесте валидаторы подписывают заранее заданные доказательства, а не согласовывают их через BFT-раунды. Открытый корневой ключ и токен не сериализуются в вывод тестового процесса.

Ограничения: прежняя регистрация/экран входа, Django users/JWT и WebSocket ещё не интегрированы. Не реализованы глобальные логины/алиасы, самостоятельное вступление узлов, выбор/смена валидаторов, BFT-раунды, ротация идентичности и отзыв ключей отдельных устройств. Logout отзывает сеанс, а не знание корневого ключа устройством. Read lease лишь проверяет подписи: реальный BFT-сервис обязан выдавать её по актуальному согласованному состоянию и обеспечивать допустимое расхождение часов. SQLite и loopback HTTP — лабораторный runtime; публичный runtime потребует TLS, разделяемого хранилища состояния логического сервера, масштабируемых лимитов и безопасной доставки клиентского кода.

Для модели недоверенных операторов клиентский код должен приходить из доверенного приложения/источника и выбирать mesh-узел только как API entry point. Произвольный узел не должен подменять исполняемый код страницы, в которую пользователь вводит пароль. Привязка адреса entry point к его ключу должна быть доверенной; самоподписанный ответ не устанавливает эту привязку. Подписи протокола не заменяют TLS для конфиденциальности bearer-токена. Публичный mesh по-прежнему не включён.


Вход этого слоя доказывает владение identity key; пароль используется только для локальной оболочки ключа. Это не реализация PAKE-обмена паролем. Подключение к продукту требует завершить доверенный каталог, выбор entry point/его ключа и адаптеры сеансов, а затем проверить весь путь вместе с реальным BFT-сервисом.


При будущем подключении к Django и интерфейсу этот scope нельзя автоматически повышать до полного входа: должны сохраняться существующие ACL, ограничения семейных аккаунтов и уже включённая 2FA. Новая проверка владения ключом пока не заменяет эти политики и не используется действующими API продукта.
