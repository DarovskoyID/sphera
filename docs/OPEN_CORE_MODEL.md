# Открытое ядро и платные модули Sfera

Все 15 модулей используют ключи на весь сервер: amoCRM, Битрикс24, 1С, документы, доски, планировщик, конференции, сообщества, каналы, боты, дневники, семейный центр, юридическая фиксация, расширенное управление узлами и дополнительные политики 2FA.

Ядро распространяется под AGPL-3.0-only. Приватный API компании расположен в отдельном репозитории `DarovskoyID/sphera-commercial`; рабочая папка `commercial-service/` исключена из Git ядра. Платёжный провайдер и цены не настроены, автоматических списаний нет.

## Установка по ключу

В «Исследовать сферу» всегда видны 15 карточек с иконками и описаниями. Администратор нажимает «Установить», вводит ключ в открывшемся окне и подтверждает установку. Узел отправляет ключ фиксированному API компании; API проверяет срок, отзыв и наличие выбранного модуля в ключе **до привязки**. Неподходящий ключ не расходуется и не привязывается.

После активации карточки разрешённых модулей получают статус «Установлен» и кнопку «Открыть». Один ключ может включать один модуль, набор или все 15. Разрешения получают все пользователи узла; их локальные права на конкретные документы, доски, сообщества и прочие данные остаются обязательными. Обычный пользователь не может активировать ключ.

Страница «Ключи и подписки» позволяет активировать дополнительные ключи. Каждый ключ привязывается к одному UUID узла. Повтор после потери ответа безопасен; ключ нельзя перенести на другой узел. Сам ключ в базе узла не хранится, в базе компании хранится только его SHA-256. Серверный credential и идентификатор повторной активации зашифрованы на узле и не возвращаются в браузер. Ключ не записывается в URL или localStorage.

## Что выполняется где

| На узле пользователя, в открытом ядре | В приватном API компании |
|---|---|
| Базовые сообщения, личные звонки, учётные записи и ACL | Выпуск ключей, привязка к узлу, срок и отзыв |
| Редакторы документов, таблиц, презентаций, досок, UI остальных рабочих пространств | Каталог и декларативные контракты всех 15 модулей |
| Хранилище, локальные алгоритмы редактирования и realtime-транспорт | Проверка платных операций и ограниченные политики рабочих пространств |
| Документы, доски, дневники, задачи, история, экспорт и удаление своих данных | CRM-адаптеры amoCRM, Битрикс24 и 1С, OAuth и бизнес-действия |
| Проверка уже включённых 2FA и ограничений детских аккаунтов | Секреты CRM в зашифрованном виде и аудит без содержимого документов |

Это разделение не делает локальные редакторы закрытым кодом: их алгоритмы входят в AGPL-ядро. Уже опубликованные исходники остаются доступными в прототипе. Форк открытого ядра технически может изменить локальную проверку лицензии, но не получит закрытые CRM-адаптеры и доступ к API компании.

Для 12 рабочих пространств прежние самостоятельные JS-пакеты заменены встроенными компонентами ядра с фиксированными ленивыми импортами. API возвращает только разрешённый `workspace` в `sfera-ui/v1`; он не выбирает URL исполняемого кода. Три CRM используют декларативные формы и действия API. Все прежние `bundle.js` этих 15 модулей на подключённом узле закрыты. Старые рабочие деревья не удаляются вместе с данными.

## Проверка доступа

- `POST /api/modules/commercial/activate/` — администратор активирует ключ; необязательный `module_id` выбирается карточкой. Ответ содержит только список разрешений.
- `GET /api/modules/commercial/` — каталог с состоянием и сроком подписок.
- `GET /api/modules/commercial/<id>/view/` — контракт интерфейса.
- `POST /api/modules/commercial/<id>/actions/<action>/` — ограниченное действие. Успех отмечен `X-Sfera-Module-Runtime: commercial-api`.

Backend узла проверяет платные POST/PUT/PATCH каждого рабочего пространства через `authorize`; наружу уходят идентификатор операции и ограниченные параметры политики, а не содержимое. Запись операций документов и досок проверяется также в общем движке, включая WebSocket. Публикация сообщений сообществ через Rust gateway проходит ту же серверную проверку. Положительное разрешение realtime может кэшироваться не более 15 секунд; интерфейс обновляет каталог каждые 15 секунд на видимой вкладке.

Локальные чтение, экспорт и удаление своих данных сохраняются после истечения ключа; прежние ACL продолжают действовать. Уже включённая 2FA, её восстановление и завершение конференции не блокируются оплатой. Базовые личные сообщения и звонки не обращаются к сервису лицензий. Отказ API компании запрещает новые платные операции, но не удаляет данные. Текущее серверное шифрование не следует называть E2EE.

В production `SFERA_LICENSE_ENFORCE` включён по умолчанию; в DEBUG отключён для локальной разработки. Узел настраивает фиксированный `SFERA_COMMERCIAL_API_URL` (HTTPS или loopback HTTP). Для прежних установок поддерживаются `SFERA_COMMERCIAL_INSTANCE_ID` и `SFERA_COMMERCIAL_API_KEY`. Новые ключи активируются через UI, credential остаётся только на backend.

## Выпуск и отзыв

На сервере компании оператор выполняет `python manage.py issue_license --modules all --expires-at <будущая-дата-ISO8601-с-часовым-поясом> --label <клиент> --key-file <новый-приватный-файл>`. Вместо `all` допустим список идентификаторов через запятую. Файл создаётся с правами 0600 и не перезаписывается; ключ не печатается в журнал. Клиенту передаётся значение `license_key` по согласованному каналу.

Отзыв ключа производится через License keys в закрытой админке; после отзыва API запрещает операции на следующем запросе. Ручной запрет конкретного модуля имеет приоритет над ключами. Истечение одного ключа не отменяет действующее разрешение от другого. Админка компании не публикуется открытым nginx-маршрутом.

`python manage.py smoke_crm` в коммерческом сервисе проверяет настоящий локальный HTTP: временный ключ, все 15 контрактов, 12 политик операций, ограничения CRM и отзыв. Клиентские лицензии не изменяются, внешние CRM не вызываются.

## Прототип и данные

Старое ядро: ветка `prototype-1` и тег `prototype-1-core-before-commercial`, коммит `a0cc146fbb61a768f4e214129edc841366a7d8d3`. Отдельные теги `prototype-1-module-<id>` сохраняют все 15 версий до коммерческих изменений; точные хеши записаны в `docs/prototypes/prototype-1.json`.

Локальные резервные копии: `output/prototype-1-before-commercial.zip` (ядро и исходники модулей) и `output/prototype-1-before-commercial.bundle` (полная история всех 16 тегов). Bundle проверен через `git bundle verify`. При восстановлении используйте отдельную папку, не сбрасывайте рабочий `main`.

Локальные Django-приложения сохраняют прежние app labels, таблицы и миграции. Миграции ключей аддитивны; документы и ключи шифрования узла не отправляются компании. Для существующих CRM команда `migrate_commercial_crm --module <id>` сначала проверяет настройки, а с `--apply` переносит только конфигурацию интеграции и её секреты. История, ACL и входящие webhook остаются на узле. Запросы CRM выполняются только по HTTPS к публичным адресам с закреплённым DNS, без редиректов; доступ к 1С внутри LAN требует отдельного транспорта.

Подробная команда выпуска ключа: [LICENSE_KEYS.md](LICENSE_KEYS.md). Неактивированные модули не появляются в навигации и не подключают фоновые загрузки своих данных. Встроенные оболочки провайдеров остаются стабильными, чтобы смена ключа не перемонтировала личные звонки; включённая 2FA продолжает проверяться. Миграция `0004_clear_legacy_installs` удаляет только старые записи `InstanceModule`/`UserModule` для локальных рабочих пространств, не их содержимое. Внутренние записи трёх прежних CRM сохраняются для входящих вебхуков и локальной истории; они не активируют коммерческий UI и не заменяют ключ.


### Удаление модуля и срок подписки

Администратор удаляет модуль кнопкой «Удалить» в каталоге для всего сервера. Данные и лицензия сохраняются; при активной подписке повторная установка не требует нового ключа. Платные операции отключаются сразу, включая открытые соединения. Дата и время окончания подписки отображаются в каталоге и разделе подписок в часовом поясе пользователя.


## Планируемые режимы установки и mesh

Корпоративная и личная установки сохраняют текущую работу вне mesh. Отдельный режим mesh point описан в [проекте архитектуры](MESH_NETWORK_ARCHITECTURE_RU.md), разделы 13–17. Пользователь выбирает entry point вручную; платные модули доступны по лицензии и состоянию установки выбранного логического сервера. Репликация и членство в кластере не передают лицензии соседям. Подбор троек учитывает близость количества оплаченных модулей после обязательных проверок ресурсов и независимости реплик. Это проект требований; новый mesh-протокол и трёхрежимный установщик пока не реализованы.


### Подтверждённый набор модулей для mesh-размещения

Коммерческий API выдаёт короткоживущий Ed25519-профиль через `/v1/mesh/attestation`: оплаченные активные модули, сроки и привязку экземпляра лицензии к сетевой идентичности узла. Срок профиля — максимум 5 минут. Ядро проверяет заранее закреплённый публичный ключ issuer и не принимает чужой профиль для другого node_id. Профиль используется для подбора кластеров и не заменяет проверку платных действий, локальные ACL, установку модуля или пользовательский выбор entry point. Подписка и права соседей не наследуются. Открытая регистрация mesh и допуск валидаторов остаются отдельными задачами.
