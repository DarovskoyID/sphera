# Открытое ядро и платные сервисы Sfera

## Зафиксированные решения

- Снимок работающей альфы: ветка `prototype-1`, коммит `a0cc146fbb61a768f4e214129edc841366a7d8d3`.
- Новая архитектура разрабатывается в `main`.
- Лицензия ядра: AGPL-3.0-only; полный текст — `LICENSE`.
- Все 15 существующих модулей становятся коммерческими сервисами.
- Подписка выдаётся на экземпляр сервера, а не на каждого его пользователя.
- Коммерческий API разворачивается на сервере компании отдельным сервисом с собственной базой и секретами.
- Содержимое досок, документов, дневников и задач хранится на узле пользователя; в базу компании оно не переносится.
- Модули клиента не получают исполняемые JS/WASM/DLL, HTML, команды ОС или произвольные URL. Клиент получает только проверяемый JSON.

## Граница ответственности

| Открытое ядро | Платный API компании |
|---|---|
| Учётные записи, идентичность, контакты, личные сообщения, звонки | Право пользоваться каждым коммерческим сервисом |
| Протоколы и транспорт, локальные разрешения, интерфейс | Подписки, лицензии, ограничения и коммерческие правила |
| Проверка декларативной схемы и отрисовка известных компонентов | CRM-адаптеры, OAuth-секреты интеграций, бизнес-действия |
| Локальное хранилище содержимого, экспорт и работа без магазина модулей | Лицензии, настройки сервисов, аудит без содержимого документов и переписки |

Отключение коммерческого API не должно блокировать базовое общение, изменять ключи или удалять данные. Текущее шифрование на сервере нельзя называть E2EE: сквозной протокол — отдельная, ещё не выполненная работа.

Для этого их данные и обязательная проверка должны быть перенесены в ядро до отключения старых backend-модулей. Базовая безопасность входа не зависит от доступности оплаты.

## Контракт

1. Администратор экземпляра получает серверный credential коммерческого API. Он хранится только на backend экземпляра, не в браузере.
2. Backend экземпляра обращается к фиксированному адресу API компании. JSON модуля не может подменять этот адрес.
3. API проверяет credential, соответствие `instance_id`, статус подписки и срок действия на каждом запросе. Флаг в открытом клиенте не даёт доступа к сервису.
4. `catalog` возвращает каталог и статус подписок без секретов.
5. `view` возвращает описание интерфейса, а не пользовательские документы; содержимое и права доступа читает ядро на своём узле. `view` возвращает документ `sfera-ui/v1` из разрешённых компонентов.
6. `action` принимает идентификатор заранее реализованного действия и валидированные значения формы. Содержимое не отправляется автоматически; передача выбранных данных для обработки требует понятного пользователю действия. Компания может видеть данные, которые получает для обработки, даже если не сохраняет их. Нет eval, произвольного HTTP-прокси и запуска команд из JSON.
7. Доступ к удалению/экспорту собственных данных нельзя связывать с продлением подписки.

## План миграции без потери функций

1. Сохранить прототип, добавить лицензию ядра и отдельный сервис подписок.
2. Реализовать и протестировать ограниченный JSON-контракт и открытый рендерер.
3. Перенести amoCRM, Битрикс24 и 1С: секреты и бизнес-адаптеры работают у компании, клиент отправляет только явно выбранные данные.
4. Перенести документы, доски и планировщик. Необходимые локальные редакторы остаются открытыми компонентами ядра; коммерческая логика идёт через API, а содержимое остаётся на узле пользователя.
5. Перенести конференции и сообщества с отдельными протоколами realtime. Не заменять их фиктивными формами CRUD.
6. Перенести остальные модули и обязательные проверки безопасности; мигрировать данные с резервной копией и проверкой целостности.
7. Только после этого отключить старую загрузку JS и backend-модулей. Старые установки нельзя считать защищённой платной архитектурой.

## Статус

Документ фиксирует целевое разделение. Существующие модули всё ещё используют legacy runtime (`import()` и локальные Django-приложения). Это не декларативные платные сервисы и их нельзя объявлять мигрированными, пока не перенесены реальные функции и данные. Цены и платёжный провайдер не выбраны; автоматическое списание не включено.

Закрытый сервис хранится в отдельном репозитории; рабочий каталог `commercial-service/` исключён из Git ядра. Эта лицензия не распространяется автоматически на другие ветки, коммерческий репозиторий и сторонние зависимости. Перенос уже опубликованного исходного кода не удаляет ранее доступные копии.

## Реализованная основа

- Официальный текст AGPLv3 и метаданные лицензии пакета.
- Приватный `DarovskoyID/sphera-commercial`: API экземпляров и подписок, ограниченный каталог, срок действия и отзыв доступа, явный реестр серверных действий.
- В открытом ядре: мост `/api/modules/commercial/`, ключи только на backend, запрет редиректов с credential, ограничение размеров запросов/ответов.
- В открытом клиенте: строгая схема `sfera-ui/v1`, безопасный рендерер и страница «Подписки на сервер».
- Временная совместимость: текущие JS-модули не отключены. Функции 15 модулей ещё не перенесены на новый API.

## Подключение API

На backend узла задаются `SFERA_COMMERCIAL_API_URL`, `SFERA_COMMERCIAL_INSTANCE_ID` и `SFERA_COMMERCIAL_API_KEY`. Последние два значения выдаёт компания для конкретного экземпляра. В браузер они не попадают. Разрешён HTTPS; HTTP допускается только для loopback на том же сервере.

Для сервера компании есть ручной workflow `Commercial API deployment`: `prepare` создаёт отдельный ключ доступа к приватному репозиторию и показывает только публичную часть, `deploy` устанавливает сервис в `/opt/sfera-commercial`. Публичному ключу нужно предоставить read-only доступ только к `sphera-commercial`. API слушает `127.0.0.1:8020`, имеет отдельные тома PostgreSQL и учётных данных. Секреты генерируются на сервере и не записываются в журнал Actions. Ядро подключается через защищённый `/etc/sfera/commercial.env` и systemd drop-in для `sfera-daphne`.

Пароль оператора остаётся в `/app/state/operator.json` внутри контейнера коммерческого API; доступ к нему — только у администратора сервера. Подписки автоматически не активируются. Развёртывание сервиса не означает завершение миграции legacy-модулей.
