# Распределённые чаты и звонки — состояние разработки 19 ноября 2026

Выбран пользователем распределённый вариант. Общий прикладной сервер на
швейцарском VPS отклонён. Независимые локальные SQL-базы служат проекциями
подтверждённого состояния, а не семью независимыми аккаунтами.

## Реализовано (публичное развёртывание регистрации описано ниже)

- Подписанные глобальные профили и неизменяемые описания личных диалогов.
  Обычный диалог создаётся подписью допущенного устройства без управляющего корня.
- Одинаковые идентификаторы пользователей/диалогов и SQL-проекции на семи точках.
- Вход через отдельные сессионные базы с подписью устройства и свежим кворумом.
- Подписанные сигналы звонков, проверка участников и межточечный relay без
  общего брокера. Передача звука/видео этим тестом не подтверждается.
- Несколько проверяемых HTTPS-источников консенсуса с переключением при отказе.
- Явный формат разрешения шифрования `sfera-mesh-cipher-scope-v2`: общий диалог,
  глобальные SDK-ключи и эпоха из истории устройств. Комната не зависит от
  выбранной точки входа; сама точка подписывает краткоживущее разрешение.
  Старый формат сохраняет прежнюю привязку к точке.
- Проверка обновления снимка перед подписью: нельзя подписать старый состав
  устройств, если финальное обновление уже увидело другое состояние.
- Реплицируемый журнал одноразовых ключей `sfera-mesh-application-key-v1`:
  SDK подписывает команду, валидаторы проверяют допуск устройства и подпись
  публичного Matrix-документа, а выдачу ключа фиксируют в общем состоянии.
  Повтор запроса возвращает прежнюю квитанцию; новая загрузка потраченного
  ключа не восстанавливает его, переименование ключа отклоняется.
- Добавлен API `distribution/keys/` (клиентский relay ключей ещё не подключён):
  mesh JWT и подписанная команда обязаны относиться к одному устройству;
  ответ 202 не содержит выданный ключ. Квитанция доступна лишь после
  подтверждения в проверенном снимке.

## Конкретный остаток до рабочего запуска

1. Подключить реализованный журнал одноразовых ключей к клиентскому relay
   с сохранением точной подписанной команды до подтверждения. Распределить
   полные SDK device-key документы и зашифрованные пакеты ключей комнат;
   отдельно реализовать явную политику fallback-ключей. Текущий журнал
   поддерживает только обычные `signed_curve25519` одноразовые ключи.
2. Передавать и восстанавливать зашифрованные сообщения между точками без
   общего серверного ключа Fernet; связать подтверждение доставки и историю.
3. Подключить создание диалогов и подпись сигналов к основному интерфейсу.
   Регистрация и вход уже подключены и проверены на семи публичных поинтах.
4. Подключить WebSocket и TURN, проверить фактическую передачу медиа.
5. Обновить обычный установщик нового поинта до текущего прикладного пакета.
   Проверить чат, звонок и отказ точки между двумя клиентами на разных VPS.
   Существующие семь VPS уже обновлены через GitHub для регистрации и входа.

Серверные исходники и подписанные пакеты опубликованы с отдельного согласия
пользователя. На всех семи VPS установлен распределённый API регистрации/входа,
исходный UI подключён к нему. Старый отказ `application_api_not_connected` устранён.
Чаты и звонки на публичных точках ещё не объявляются работающими.

Журнал ключей имеет лабораторные пределы: 512 записей, 512 КиБ журнала,
512 когда-либо загруженных ключей на устройство и проверку общего снимка
перед добавлением записи. Сжатие истории с сохранением защиты от повторной
выдачи пока не реализовано. Поэтому он не заявляется безлимитным production
хранилищем, даже несмотря на успешный прогон семи точек.

## Подключение регистрации — следующий этап 19 ноября

В коде формы добавлен явный распределённый режим, определяемый маршрутом
`/api/distribution/config/`. В нём старые маршруты почтовой регистрации не
используются. Браузер создаёт разные ключи владельца и устройства, сохраняет
их зашифрованными до первого запроса, отправляет только публичный подписанный
пакет и после подтверждения проходит обычный device challenge/login.
При обрыве сохраняется та же учётная запись. Между вкладками действует lock.
Для известных семи поинтов используется включённый в сборку публичный каталог
ключей; его ключи дополнительно проверяются свежей подписью entry probe.

Серверный `ApplicationRegistration` полностью проверяет пакет перед первой
публикацией, затем подтверждает аккаунт, профиль и устройство по отдельности.
Промежуточный ответ 202 не выдаёт пользователя или сессию. Добавлены отдельные
настройки и маршруты Django-сервиса с локальными секретами и отдельной базой
проекции. Проверка Django `check` прошла.

Клиентский тест проверил реальные подписи, локальную запись до запроса и
повтор после искусственного обрыва. Три Python-теста проверили стадии,
конфликты имени и отклонение повреждённых подписей до публикации. Обновлённый
живой тест на четырёх валидаторах подтвердил регистрацию тем же серверным
кодом и одинаковые проекции семи точек.

Для смены защищённого verifier подготовлен отдельный root-authorized контракт
`sphere-point-verifier-transition-v1`. Он сохраняет старый бинарный файл,
все базы/ключи и release floor, требует остановленного supervisor/runtime,
проверяет старый admission и точные хэши, сохраняет закрытую квитанцию и
позволяет завершить прерванную пару записей без отката данных. Все 33 теста
со связанными проверками release/supervisor прошли в локальном Linux.

## Исправление каталога модулей — 20 ноября 2026

В распределённом URLconf отсутствовали `/api/modules/` и `/api/modules/public/`.
Теперь подключены существующие обработчики каталога реально установленных модулей.
Обычный пользователь не получает полномочий установки: `can_manage=false`.
Загрузка модулей из Git в immutable release-каталог отключена; полноценный
операторский runtime установки модулей остаётся отдельной незавершённой задачей.

`/api/auth/me/` явно сообщает возможности поинта. При распределённом режиме
первоначальная загрузка UI не вызывает отсутствующие персональные API контактов,
блокировок, эмодзи и настроек. Это не реализация этих API и не обещание готовых чатов.
Списки предыдущего сервера очищаются при таком переключении.

Повторный вход также исправлен: локальная запись устройства выбирается по
подписанному device ID, а не по IP, который может совпадать у нескольких устройств.
Криптографические проверки и ограничения сессии сохранены. Реальный JWT-тест
с несколькими устройствами на одном IP прошёл. В браузере повторный вход в
ранее созданный аккаунт и перезагрузка прошли без прежнего окна ошибки.

Проверены все семь поинтов: авторизованный каталог — 200, анонимный — 401,
публичный каталог — 200. После проверки выполнен выход из тестового аккаунта.
