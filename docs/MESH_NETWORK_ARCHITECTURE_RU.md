# Архитектура mesh-сети мессенджера

Дата: 19 октября 2026 года. Статус: проект архитектуры по обсуждению; этот документ не означает, что протокол уже реализован.

Исходная схема: «схема антронакс (3).svg». Цвета стрелок служат только для читаемости и не обозначают разные типы протокола.

## 1. Согласованные требования

- Сеть — большой граф из множества кластеров по три логических сервера, а не фиксированная сеть из шести серверов.
- Каждый сервер хранит собственные данные и реплики данных двух соседей своего кластера.
- Логический сервер может состоять из одной машины или целой сети машин; его сетевой идентификатор не зависит от конкретного процесса, IP или машины.
- История хранится распределённо, связана в обоих направлениях и доступна с начала и с конца.
- Есть отдельная точка доступа к последним 100 сообщениям.
- Личный ключ защищает историю пользователя; общего секретного ключа разработчика или сервера для генерации нет.
- Вход возможен через любой сервер сети и с нового устройства.
- Пропуски истории при потере целого кластера должны обнаруживаться без последовательного чтения всей переписки.
- При потере участника кластер восстанавливает тройку. Допускается временный участник из другого кластера, работающий сразу в двух кластерах до появления нового подходящего сервера.

Далее описаны предлагаемые механизмы реализации этих требований. Размер блоков, параметры криптографии, правила приёма узлов и конкретный протокол консенсуса ещё требуют выбора и проверки.

## 2. Уровни сети и идентификаторы

| Уровень | Назначение |
| --- | --- |
| Машина / процесс | Реальное выполнение, диски, соединения |
| Логический сервер (`node_id`) | Участник mesh со своей устойчивой криптографической идентичностью; внутри может масштабироваться на несколько машин |
| Кластер (`cluster_id`) | Группа из трёх разных логических серверов с взаимной репликацией |
| Mesh | Граф связей кластеров, поиск данных, маршрутизация и обмен |

Смена IP, переезд машины и замена участника кластера не должны менять идентификаторы пользователя, диалога и блока истории. Адреса хранения разрешаются отдельно: `block_id → cluster_id → текущие node_id/endpoints`.

Полносвязность всей сети и хранение всей истории на каждом узле не требуются. Физически связанные машины не считаются независимыми копиями: при подборе тройки учитываются общие диски, площадки, питание и оператор.

## 3. Аккаунт и вход через другой сервер

Аккаунт принадлежит сети, а не серверу регистрации. У него постоянный `user_id`; сервер A или Б — точка подключения.

Распределённая запись аккаунта содержит:

- `user_id`, публичные ключи идентичности и версию записи;
- привязку логина к идентификатору по выбранному правилу пространства имён;
- сведения протокола аутентификации, но не открытый пароль;
- зашифрованный личный ключ, публичную соль, параметры KDF и версию формата;
- ссылки на индекс диалогов и местоположение актуальных записей;
- подписи и сведения об изменении/отзыве устройств.

Сервер Б находит запись через распределённый каталог, например DHT с аутентифицированными записями. Последовательный обход всех серверов не используется. Bootstrap-узлы помогают войти в сеть, но не являются единственным источником аккаунтов или владельцами ключей.

Новое устройство получает зашифрованную копию личного ключа и разблокирует её локально. Пароль и открытый личный ключ не отправляются произвольному серверу Б. Для проверки входа нужен отдельный проверенный протокол, например PAKE; его выбор не подменяется простым сравнением хеша пароля.

Вход на Б не переносит автоматически историю и не меняет кластер хранения. Несколько устройств могут подключаться одновременно.

Метаданные аккаунта, зашифрованный ключ, каталог размещения и контрольные точки истории реплицируются за пределами домашнего кластера. Предложение: минимум в трёх независимых кластерах. Это отдельная политика для малых метаданных; она не означает полную межкластерную копию всех сообщений.

Глобальная уникальность коротких логинов и защита регистрации от захвата имени ещё не определены; сам по себе DHT не решает конкурирующую регистрацию.

## 4. Ключи и шифрование

При регистрации устройство создаёт случайный личный корневой ключ криптографическим генератором ОС. Из пароля и случайной публичной соли через Argon2id получается ключ защиты; им шифруется личный ключ с аутентификацией. Общего секрета генератора нет.

При входе на другом устройстве из того же пароля, соли и параметров получается тот же ключ защиты, которым открывается существующий личный ключ. Сам случайный личный ключ не генерируется заново. При смене пароля обновляется его зашифрованная оболочка, а не вся история.

Личный корневой ключ защищает личный архив и ключевой материал. Для сообщений применяются отдельные ключи по назначению и версии; собеседнику не передаётся корневой ключ, открывающий всю историю. Доставка собеседникам требует отдельного E2EE-протокола диалогов/групп и поддержки устройств. Постоянный архивный ключ сам по себе не обеспечивает прямую секретность при последующей компрометации.

Серверы реплицируют шифротекст. Хеши хранения вычисляются по шифротексту и каноническим заголовкам, поэтому проверка копий не требует расшифровки. Для каждой операции шифрования соблюдаются требования алгоритма к уникальности nonce.

Сброс пароля без старого пароля не восстанавливает ключ автоматически: нужен код восстановления или подтверждение с уже доверенного устройства. При смене оболочки старые сохранённые копии могут оставаться защищены старым паролем; отзыв устройства требует отдельной ротации ключей, а не только смены пароля.

## 5. Двунаправленная история и последние 100 сообщений

Логически сообщения диалога образуют двунаправленный список. Для хранения и передачи они объединяются в упорядоченные блоки. Логические позиции сообщений и связи между блоками позволяют читать историю в обе стороны без отдельного сетевого запроса на каждое сообщение.

Предлагаемый манифест диалога:

```text
dialog_id
version / epoch
head_block_id              # начало истории
tail_block_id              # последний блок
last100_start_cursor       # block_id + позиция первого из последних 100
last100_end_cursor         # конец актуального окна
committed_sequence         # последняя подтверждённая позиция
message_count
history_merkle_root
availability_checkpoint
signature / commit_certificate
```

Соответствие рисунку: `START_MESSAGE_ADRESS` — начало; `START_last100_messsages` — начало окна; `BACKWARD_ADRESS_LAST100_MESSAGES` — обратная точка доступа к концу окна/истории. Точный смысл последнего поля нормализован здесь как предложение, поскольку рисунок не задаёт формат курсора.

У каждого блока есть устойчивый `block_id`, `dialog_id`, диапазон позиций, число событий, хеш содержимого и ссылки `prev_block_id` / `next_block_id`. У головы предыдущий адрес пуст, у хвоста следующий пуст. Последние 100 могут занимать несколько блоков; курсор содержит смещение, а не только адрес сервера. Если сообщений меньше 100, окно начинается с головы.

Нельзя взаимно включать хеш следующего и предыдущего блока в их собственные content-addressed идентификаторы: получится циклическая зависимость. Поэтому идентификаторы блоков устойчивые и независимые от хеша содержимого, а изменяемые связи хранятся в подписанном/подтверждённом индексе с версиями. Содержимое закрытого блока неизменно; расширение истории меняет хвост и индекс.

Одновременные отправки получают единый подтверждённый порядок в пределах диалога/его раздела, но не глобальный порядок всей сети. Повторы устраняются по `message_id`. Редактирования и удаления — отдельные события и подтверждённые отметки, чтобы легальное удаление не выглядело потерей данных.

## 6. Как обнаруживать потерю без обхода всей истории

### 6.1. Возможности и пределы хешей

По одному началу и концу обычного двунаправленного списка невозможно установить наличие всех промежуточных данных. Даже корректный ранее сохранённый корневой хеш не доказывает, что данные сейчас доступны: узел может хранить хеш, но потерять шифротекст.

Хеш позволяет проверить целостность полученных данных и сопоставить состояния. Он не восстанавливает утраченный текст и не отличает временную сетевую недоступность от физической потери диска.

### 6.2. Индекс Merkle и независимый учёт размещения

Поверх двунаправленного списка строится сбалансированный аутентифицированный индекс Merkle по диапазонам истории. Лист связывает `dialog_id`, `block_id`, диапазон позиций, количество событий и хеш шифротекста. Подписанный манифест фиксирует корень, размер и версию. Размещение хранится в отдельном версионируемом каталоге, чтобы переезд блока не требовал перехешировать его содержимое.

Начальная и конечная точки относятся к одному подтверждённому манифесту. Клиент может запросить доказательства для границ и нужных диапазонов. Если корни двух копий различаются, сравнение хешей поддеревьев локализует расхождения без загрузки всех сообщений. Для одного диапазона доказательство имеет логарифмический размер; для большого числа разрозненных потерь объём работы растёт с числом затронутых диапазонов, вплоть до линейного худшего случая.

Отдельно поддерживается обратный индекс `cluster_id → блоки и диапазоны диалогов`. Он, манифесты и узлы Merkle реплицируются вне кластера, содержащего сообщения. При недоступности тройки по этому индексу находятся затронутые диалоги и участки; не требуется читать каждый диалог от головы до хвоста.

Факт доступности подтверждается проверками реплик и получением данных, а не только совпадением корневого хеша. Периодическая проверка дисков и контрольные чтения нужны даже у узлов с действующим heartbeat. Без сканирования или проверяемого протокола хранения нельзя непрерывно гарантировать наличие каждого байта.

### 6.3. Отказ целого кластера

1. Детектор фиксирует недоступность всех трёх участников. Сначала это статус «временно недоступно», а не доказанная безвозвратная потеря.
2. Из внешнего индекса размещения получаем затронутые блоки, позиции и ожидаемые хеши.
3. Сопоставляем их с подписанными манифестами и доказательствами Merkle; обозначаем пропуски между доступными участками с начала и конца.
4. Ищем другие копии: резервные реплики, уже подтверждённые миграции, зашифрованные копии на устройствах. Найденное принимаем только после проверки ожидаемого хеша и происхождения.
5. Если подходящих копий нет, показываем утраченный/недоступный диапазон, сохраняем его идентификаторы и возможность последующего восстановления. Не склеиваем края так, будто сообщений никогда не существовало.

Если все три копии шифротекста находились только в погибшем кластере, восстановить его из хеша невозможно. Для гарантии переживания потери целого кластера требуется ещё одна независимая копия шифротекста вне него либо заранее рассчитанное межкластерное избыточное кодирование. Репликация одних метаданных гарантирует обнаружение, но не восстановление.

## 7. Репликация и подтверждение записи

Предложение: внутри тройки используется проверенный протокол консенсуса; запись подтверждается после устойчивой фиксации на большинстве 2 из 3. Третий участник догоняет журнал. Поэтому три копии — целевое устойчивое состояние, а в момент подтверждения запись может иметь две устойчивые копии.

Потеря одного участника сохраняет кворум. Потеря двух при такой модели останавливает подтверждение новых записей до безопасного восстановления. Оставшийся участник не может самостоятельно объявить новую тройку и продолжить против возможного старого большинства.

Граница консенсуса и соответствие диалогов разделам хранения ещё требуют проектирования. Вся mesh-сеть не превращается в один общий кластер консенсуса.

## 8. Самовосстановление состава кластера

Пример: A/B/C теряет C, а D/E/F пока здоров.

1. A и B обнаруживают сбой и подтверждают изменение состояния кворумом. Один таймаут не доказывает окончательную смерть C.
2. Ищут свободный принятый в сеть сервер с достаточными ресурсами. Если его нет — кандидата из другого кластера, например D.
3. D остаётся участником D/E/F и получает отдельную временную роль в A/B/D. Для двух кластеров ведутся раздельные журналы, данные, права и учёт ресурсов. В одном кластере D имеет только один голос независимо от количества его машин.
4. D сначала подключается как догоняющий участник без голоса, получает снимок и последующие записи от A/B, проверяет хеши и достигает согласованной позиции.
5. Только после синхронизации выполняется безопасная смена членства штатным механизмом консенсуса. Старый C исключается по версии состава; его позднее возвращение не создаёт параллельный кластер с правом записи.
6. После появления нового принятого сервера G он аналогично догоняет A/B/D. Затем подтверждается переход к A/B/G; D освобождает временную роль после проверки новых копий и завершения передачи.

Временный участник выбирается по независимости отказов, свободному месту, задержкам и лимитам нагрузки. Предлагаемый предел — участие максимум в двух кластерах, как в требовании. Нельзя перегружать исправный кластер ради восстановления другого или считать одного и того же node_id двумя независимыми репликами одной тройки.

Если кандидатов нет, A/B остаётся в деградированном режиме с явным статусом и повторяет поиск с задержкой. Восстановление не может гарантироваться при отсутствии ресурсов. При массовых отказах нужны приоритеты и ограничение параллельных переносов.

Утрата кворума требует отдельной процедуры аварийного восстановления и защиты от старых участников; автоматическое добавление новых соседей не решает эту проблему само по себе.

## 9. Доверие и границы безопасности

Узлы аутентифицируются криптографическими идентификаторами, записи маршрутизации и метаданные имеют подписи, версии и защиту от отката. Серверы не получают личные ключи расшифровки. Необходимо определить правила вступления узлов и защиту от захвата множества идентичностей одним оператором.

Обычный консенсус большинства переносит сбои и разделения сети, но не обеспечивает защиту от произвольного сговора злонамеренных участников. Если тройки формируются из недоверенных публичных серверов, модель доверия и протокол нужно выбрать отдельно. Подпись пользователя защищает авторство, но сама по себе не обеспечивает доступность данных.

## 10. Что предстоит определить перед реализацией

- Единица цепочки и Merkle-индекса: личный архив, диалог или обе проекции. В схеме указаны записи пользователя; двунаправленность и пропуски обсуждались для диалога. Здесь предложен индекс на диалог и пользовательский список ссылок на диалоги.
- Распределённый каталог, правила имён, bootstrap и обновление местоположения.
- Протокол входа без передачи пароля чужому серверу, E2EE, восстановление и отзыв устройств.
- Размеры блоков, порядок событий, индексы, формат подписей и контрольных точек.
- Где хранится активный хвост и как атомарно переключается запись на следующий блок/кластер.
- Политика межкластерных копий сообщений: только обнаружение потери или гарантия восстановления.
- Консенсус, безопасная смена состава, критерии сбоев и процедура потери большинства.
- Кто может предоставлять узлы, какие участники считаются доверенными и как учитываются общие зоны отказа.

## 11. Проверяемые сценарии готовности

- Новое устройство входит через другой сервер и читает старую историю без передачи открытого личного ключа серверу.
- История читается от головы вперёд и от хвоста назад; последние 100 доступны без полного обхода.
- Потеря одного узла запускает безопасный подбор и синхронизацию замены.
- Один node_id временно работает в двух кластерах; после появления нового узла временная роль освобождается без потери подтверждённых данных.
- Разделённая сеть не создаёт два независимо подтверждающих запись состава одного кластера.
- Потеря целой тройки обнаруживает затронутые диапазоны через внешний индекс; интерфейс показывает пропуски, а не пустую успешную историю.
- Совпадающий Merkle-корень при отсутствующем шифротексте не трактуется как доказательство доступности.
- Восстановленная копия проверяется по ожидаемому хешу; смена пароля и восстановление членства не меняют историю задним числом.

- Доказательства включения и согласованности Merkle: https://www.rfc-editor.org/rfc/rfc9162.html (описанный там журнал — пример стандартного механизма доказательств, а не готовый протокол этого мессенджера).
- Кворум и потеря большинства на примере etcd: https://etcd.io/docs/v3.7/op-guide/failures/

Документ фиксирует требования и предложения; параметры production-протокола и его гарантии должны подтверждаться реализацией и испытаниями.


## 13. Три режима установки и изоляция mesh

Дополнение требований от 19 октября 2026 года.

Единый install-скрипт должен предлагать три явных варианта:

```text
Выберите режим установки:
1. Корпоративный
2. Личный
3. Mesh point
```

| Режим | Поведение |
| --- | --- |
| Корпоративный (`corporate`) | Существующий самостоятельный сервер и текущая бизнес-модель. Не вступает в mesh, не размещает чужие реплики и не публикует аккаунты в mesh-каталог |
| Личный (`personal`) | Существующая работа личного узла. Не вступает в mesh и не передаёт свои данные в mesh автоматически |
| Mesh point (`mesh`) | Участник описанного здесь графа, с поиском кластера, репликацией, сетевым аккаунтом и ручным выбором точки входа пользователем |

Первые два режима сохраняют текущие возможности и проверки подписок. Их разделение не вводит новые ограничения числа пользователей или функций без отдельного требования. Изоляция от mesh не запрещает существующие явно настроенные подключения, которые уже доступны сейчас.

Выбор сохраняется в конфигурации установки; неинтерактивная установка должна принимать явный параметр режима. Повторный запуск не должен молча менять режим существующего узла. Переход между самостоятельной установкой и mesh — отдельная явная процедура с проверкой идентичности и миграции данных. Автоматического включения прежних установок в mesh нет.

В mesh-режиме установщик должен проверять готовность реализации протокола, задавать bootstrap и идентичность node_id, проверять ресурсы, показывать условия репликации и запускать поиск подходящей тройки. Пока протокол не реализован, установщик не должен выдавать обычный standalone-запуск за работающий mesh point. Этот раздел — требования к будущему установщику, а не заявление о наличии такого скрипта в текущей версии.

## 14. Ручной выбор entry point и доступ к модулям

Пользователь сам выбирает сервер входа. Система не переключает его на другой сервер автоматически ради оплаты, баланса нагрузки, наличия модуля или отказа текущего entry point. Можно показать доступные адреса и предложить переподключение, но переход требует действия пользователя. Повторное соединение с тем же логическим node_id и переключение внутренних машин этого node_id не являются выбором другого сервера.

Если текущий entry point недоступен, интерфейс показывает потерю соединения и предлагает выбрать другой. Внутренняя маршрутизация к блокам истории и восстановление состава кластера работают автоматически и не меняют выбранную пользователем точку входа.

Модуль доступен пользователю только при одновременном выполнении условий:

```text
модуль оплачен и разрешён на выбранном entry point
AND модуль установлен/включён на этом сервере
AND пользователь имеет необходимые права на операцию и данные
```

Личный аккаунт, подписка другого сервера и наличие реплики модуля у соседа не открывают модуль на текущем entry point. Если пользователь работал с доской на A, а затем сам вошёл на Б без оплаченного и включённого whiteboard, редактор досок на Б недоступен. Интерфейс объясняет причину и может предложить ручной выбор другого сервера; автоматического перехода на A нет.

Данные при этом не удаляются. Предусмотренные текущей моделью чтение/экспорт/удаление своих данных после окончания подписки остаются отдельными операциями открытого ядра с ACL, а не способом открыть платный модуль. В новом сетевом протоколе нужно отдельно определить безопасный доступ к таким архивам без запуска платного редактора.

Проверка платных действий выполняется на backend и realtime-каналах от идентичности выбранного entry point. Пересылка запроса к оплаченному соседу не должна обходить ограничения Б. Репликация шифротекста — инфраструктурная функция ядра и не даёт права выполнять платные бизнес-действия на реплике.

## 15. Подбор кластеров по оплаченным модулям

Кластеры формируются из серверов с максимально похожим количеством оплаченных модулей. В расчёте учитываются действующие разрешения коммерческого сервиса, а не просто скачанный код, установленные пакеты или заявления узла.

Предлагаемый алгоритм:

1. Отобрать допустимых кандидатов: разные node_id, достаточно места и пропускной способности, подходящие независимые зоны отказа, совместимая версия протокола, допустимое число кластеров и подтверждённая принадлежность сети.
2. Среди допустимых составов минимизировать разброс числа активных оплаченных модулей: `max(count) - min(count)`.
3. При одинаковом разбросе предпочитать более схожие наборы module_id, затем учитывать задержку, запас ресурсов и стабильность.
4. При отсутствии точного совпадения выбирать ближайший допустимый состав; при нехватке трёх безопасных участников показывать ожидание/деградированное состояние. Само по себе отсутствие одинакового набора не должно создавать выдуманную реплику.

Количество модулей — основной коммерческий критерий, совпадение их состава — предлагаемый дополнительный. Например, сервер с тремя модулями предпочтительнее объединять с узлами с тремя, чем с узлами с пятнадцатью; при равном числе предпочтителен совпадающий набор. Независимость реплик и возможность реально хранить данные обязательны и не отменяются ради совпадения подписок.

Для временной замены потерянного соседа действуют те же правила. Восстановление реплик имеет приоритет над ожиданием идеального коммерческого совпадения; выбор ближайшего допустимого кандидата не переносит его подписки остальным участникам.

Изменение набора подписок не приводит к немедленной перестройке кластера. Нужны период устойчивости, задержки и контролируемая перебалансировка после синхронизации. Иначе истечение ключей и массовое продление вызовут постоянные переносы данных. Любая перебалансировка сохраняет node_id выбранного entry point и выполняется через безопасное изменение состава.

Подтверждение оплаченного набора должно быть версионируемым и ограниченным по сроку, выдаваться коммерческим API и не содержать ключ активации или пользовательские данные. Формат такого подтверждения ещё предстоит реализовать. Отказ сервиса лицензий не должен удалять реплики, останавливать базовую переписку или мгновенно распускать кластеры; новые платные операции следуют действующей политике авторизации, а подбор использует последнее допустимое подтверждение либо ждёт проверки.

## 16. Соответствие бизнес-модели

- Открытое AGPL-ядро: базовое общение, mesh-транспорт, каталог, хранение шифротекста, проверка целостности и восстановление реплик.
- Все текущие платные модули сохраняют лицензирование на весь логический сервер, привязку ключа к его устойчивой идентичности и проверку через коммерческий API.
- Несколько физических машин одного node_id не создают несколько лицензируемых серверов; разные node_id требуют собственных разрешений.
- Участие одного сервера в двух кластерах не даёт его соседям бесплатных модулей. Репликация не копирует права лицензии, credentials и секреты CRM.
- Вход пользователя через новый entry point не переносит ключ подписки с предыдущего сервера.
- Работа корпоративного и личного режимов не зависит от готовности mesh; данные этих установок автоматически в mesh не попадают.
- Данные пользователей остаются на узлах сети, коммерческий API получает необходимые для лицензирования метаданные, а не содержимое сообщений.

## 17. Дополнительные сценарии приёмки

- Установщик предлагает все три режима и сохраняет выбор; прежняя установка не становится mesh point после обычного обновления.
- Corporate/personal не вступают в mesh и не принимают mesh-реплики.
- Выбор Б без нужного модуля закрывает модуль, даже если на A или у соседей он оплачен.
- Действие через backend или WebSocket не обходит ограничение entry point; внутренний прокси не подставляет лицензию другого узла.
- При отказе entry point пользователь получает предложение выбрать сервер, но остаётся без автоматического переключения.
- Кандидаты с близким числом оплаченных модулей предпочтительны; небезопасный состав не принимается ради коммерческого совпадения.
- Истечение лицензии не удаляет данные и не запускает бесконечное перемещение кластеров.


## 18. Уточнение: открытое участие операторов

Пользователь подтвердил: mesh-сервер может добавлять любой желающий. Поэтому допущение о только честных операторах неприменимо. Обычное большинство 2 из 3 описывает отказоустойчивость при поломках, но не является выбранным защищённым протоколом публичной mesh. Разделы 7–8 должны реализовываться с учётом этого уточнения.

Согласовано: сохранить тройки для хранения шифротекста. Валидаторы работают на тех же mesh-серверах, отдельные физические серверы не обязательны. Согласование состава, версий и контрольных точек выполняют BFT-комитеты минимум из четырёх разных node_id из нескольких троек; одна тройка не образует достаточный комитет для допуска одного злонамеренного валидатора. Для допуска одного византийского участника стандартная модель PBFT требует минимум четырёх валидаторов. Подписи пользователей проверяются независимо от операторов хранения. Комитет не доказывает физическое наличие данных и не восстанавливает утраченный шифротекст.

Открытое подключение не означает автоматическое включение любого нового node_id в доверенный набор валидаторов. Нужны правила защиты от Sybil, формирования и смены комитетов, независимости операторов и восстановления доверия. Эти правила не выбраны; до их выбора публичный production mesh не включается. Количество платных модулей служит критерием размещения, но не доказательством независимости или честности оператора.

Основание ограничения PBFT: https://pdos.csail.mit.edu/6.824/papers/castro-practicalbft.pdf
