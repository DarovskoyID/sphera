# Модули Сферы

Сфера состоит из **ядра** и **модулей**.

**Ядро** живёт в ветке `main`. В него входят:
- авторизация;
- друзья;
- личные переписки;
- звонки;
- SDK модулей;
- реестр модулей (`sfera_modules`).

**Модули** лежат каждый в своей ветке `module/<id>`:

| Модуль | Ветка | Django-приложение | Что даёт |
|---|---|---|---|
| Серверы | `module/servers` | `sfera_servers` | сообщества с текстовыми и голосовыми каналами, роли, приглашения, поиск серверов |
| Каналы | `module/channels` | `sfera_channels` | личные ленты: посты, подписки, комментарии, поиск каналов и постов |
| Боты | `module/bots` | `sfera_bots` | Сфероник, редактор ботов, Bot API, SDK |
| Семейный центр | `module/family` | `sfera_family` | детские аккаунты, одобрение друзей, геолокация семьи |
| Личные дневники | `module/diary` | `sfera_diary` | приватные записи с задачами, геометками и файлами |
| Несколько серверов | `module/multiserver` | — | выбор сервера Сферы на экране входа, свои TURN/STUN |
| Конференции | `module/conference` | `sfera_conference` | внутренние, приватные и внешние видеоконференции, гости по ссылке, зал ожидания |
| Доски | `module/whiteboard` | `sfera_whiteboard` | диаграммы в духе draw.io: фигуры, связи, стикеры, совместная работа, экспорт |
| Планировщик задач | `module/planner` | `sfera_planner` | проекты, канбан, список, календарь, повторы и напоминания |
| Интеграция с 1С | `module/onec` | `sfera_onec` | справочники и документы через OData, уведомления из 1С |
| Интеграция с amoCRM | `module/amocrm` | `sfera_amocrm` | сделки из переписки, поиск по CRM, web hooks |
| Интеграция с Битрикс24 | `module/bitrix` | `sfera_bitrix` | лиды, сделки и задачи из переписки, события портала |
| Протоколы переписки | `module/legal` | `sfera_legal` | хеш-цепочка сообщений, протокол для суда, подписи сторон, публичная проверка по коду |
| Документы | `module/office` | `sfera_office` | документы, таблицы с формулами и презентации с совместным редактированием, комментарии, история версий, экспорт |
| Двухфакторная аутентификация | `module/totp` | `sfera_totp` | вход по коду из Google Authenticator, резервные коды, обязательность для всех и блокировка приложения до подключения |

Модули не зависят друг от друга. Если модуль умеет больше рядом с другим, он проверяет, есть ли тот на сервере. Например, у семьи появляется семейный сервер, когда развёрнут модуль серверов. Бот может писать в каналы серверов тоже только при развёрнутом модуле серверов.

## Как пользователь ставит модули

1. **Открывает каталог.** Суперпользователь видит в «Исследовать сферу» все ветки `module/<id>` репозитория с версией из их `module.json` — каталог перечитывается раз в 5 минут. Остальные видят модули, которые уже есть на сервере.
2. **Устанавливает модуль.** Сервер забирает ветку из репозитория в `modules/<id>`, собирает фронтенд модуля, применяет миграции и перезапускается, чтобы Django загрузил приложение модуля. Карточка показывает «Загрузка из репозитория…» и «Перезапуск сервера…»; интерфейс модуля появляется сам, без перезагрузки страницы. Зависимости ставятся вместе с модулем.
3. **Обновляет модуль.** Если в ветке новая версия, на карточке появляется «Обновить» (v1.0.0 → v1.1.0) — сервер переходит на голову ветки тем же путём.
4. **Удаляет модуль.** Интерфейс исчезает, API модуля начинает отвечать 403, **все его данные на сервере удаляются**: сначала вызывается хук `PURGE_DATA` самого модуля (кеши, файлы вне моделей), затем очищаются все таблицы его Django-приложения (`sfera_modules/purge.py`). Схема остаётся — миграции не откатываются, так что повторная установка начинается с пустых таблиц. Карточка предупреждает об этом и просит подтверждение. Хуки удалённого модуля ядро больше не спрашивает, даже если процесс ещё не перезапущен.
5. **Поиск.** Строка поиска в «Исследовать сферу» есть, только пока установлен хотя бы один модуль с поиском: серверы или каналы.
6. **Защита детей.** Семейный центр нельзя удалить, пока пользователь состоит в семье. Ограничения детского аккаунта работают независимо от того, что установлено.

Все, у кого уже были данные модуля, получили его автоматически в миграции `install_for_*`.

## Устройство ветки модуля

```
module.json                 id, name, version, sdkVersion, deps, backendApp, urlPrefix, icon, preAuth (UI и на экране входа: auth.footer, auth.route)
package.json                 необязательно: npm-зависимости фронтенда модуля (ставятся при сборке модуля)
backend/<django_app>/        models, migrations, urls.py, routing.py (WS), apps.py (хуки), tests.py
frontend/index.tsx           export default defineModule({ id, setup(ctx) { … } })
monitoring/grafana/*.json    дашборды Grafana модуля (папка модуля в Grafana)
monitoring/alert_rules.yml   алерты Prometheus модуля (необязательно)
.github/workflows/module.yml CI модуля: собирает main + этот модуль и гоняет его тесты
```

### Бэкенд

Загрузчик (`sfera_modules/loader.py`) находит `modules/*/module.json` и делает три вещи:
- добавляет `backendApp` в `INSTALLED_APPS`;
- монтирует `urls.py` по `urlPrefix`;
- подключает `routing.py`. WebSocket-маршруты модулей идут под `/ws/m/...`, nginx отправляет их в Django.

Модуль общается с ядром только через `sfera_modules.hooks`:
- **Сигналы:** `message_created`, `conversation_opened`, `user_blocked`/`user_unblocked`, `module_installed`/`module_uninstalled`.
- **Реестры:** `PROFILE_EXTRAS`, `DATA_EXPORT`, `METRICS`, `HAS_DATA`, `IS_MANAGED`, `CAN_UNINSTALL`, `WS_AUTHORIZE`, `KAFKA_HANDLERS`, `ENCRYPTED_DATA`, `LOGIN_GUARD`, `SECOND_FACTOR`, `ACCESS_GUARD`, `PURGE_DATA`.
- **Доступ:** три последних реестра закрывают вход и работу в приложении, и решает их ядро, а не интерфейс:
  - `LOGIN_GUARD` — `fn(user, request) -> dict | None`. Пароль уже проверен; непустой ответ уходит клиенту с кодом 409, и токен не выдаётся.
  - `SECOND_FACTOR` — `fn(challenge, code, request) -> user | None`. Ядро зовёт его из `POST /api/auth/login/2fa/` и выдаёт токены только за вернувшийся аккаунт.
  - `ACCESS_GUARD` — `fn(user_id) -> dict | None`. Зовётся из `BanGuardMiddleware` перед каждым запросом `/api/` и из WebSocket-аутентификации. Непустой ответ — тело ответа 403; его ключ `allow` перечисляет префиксы путей, которые остаются открытыми, чтобы аккаунт мог снять блокировку. Всегда открыты `/api/modules/` и точные пути `/api/auth/me/`, `/api/auth/logout/`, `/api/auth/ban-status/`. Хук зовут на каждом запросе — модуль обязан кешировать свой ответ.
- **Сервисы:** `hooks.provide(name, impl)` / `hooks.service(name)`.
- **Пуш клиенту:** `hooks.push_to_user(user_id, event, payload)`.

Метрики модуль отдаёт через `METRICS`: `tables` (строки в `sfera_db_rows`), `prometheus` (список серий `{name, type, value, help, labels}`) и `status` (карточки на `/status/`). Ядро само ничего не знает о метриках модулей.

Эндпоинты модуля закрываются декоратором `requires_module('<id>')`, WebSocket — функцией `ws_has_module`. Переменная `SFERA_MODULES_ENFORCE=0` отключает проверку, и тогда все развёрнутые модули считаются установленными.

### Фронтенд

Фронтенд модуля не входит в сборку ядра. Сервер собирает его отдельно (`scripts/modules/build-module.mjs`, esbuild) в один ES-модуль `modules/.bundles/<id>/<коммит>-<метка>.js` и отдаёт по `/api/modules/<id>/bundle.js?v=…`; клиент загружает его через `import()`. React и `@sfera/sdk` в бандл не попадают — модуль получает копии ядра из `window.__SFERA_SHARED__` (`src/core/modules/shared.ts`), поэтому хуки, контекст и слоты общие. Остальное (lucide-react, зависимости из `package.json` модуля) бандлится.

Модуль импортирует из ядра только `@sfera/sdk` (`src/sdk/index.ts`). В `setup(ctx)` он регистрирует:
- **слоты интерфейса:** `nav.rail`, `nav.railScroll`, `rail.addAction`, `main.view`, `settings.page`, `explore.card`, `explore.search`, `chat.composerAction`, `profile.section`, `sidebar.userPanel`, `picker.stickers`, `app.overlay`, `app.provider`, `auth.footer`, `auth.route` (полноэкранная страница вместо формы входа, например вход гостя в конференцию по ссылке);
- **сокет модуля:** `openModuleSocket({ path: '/ws/m/<id>/…', onFrame, onStatus })` — переподключается сам, `send(frame)` отправляет JSON;
- **подписки на события:** `ctx.onWs('signaling', 'module:<event>', …)`;
- **хуки жизненного цикла:** `ctx.onLifecycle('logout' | 'callStart' | 'mute' | 'deafen' …)`;
- **переводы:** `ctx.strings(...)`.

Маршрут модуля записывается в `currentServer` как `<id>:<что-угодно>`, например `diary:<uuid>`.

## Разработка и деплой

Модули заранее не разворачиваются: их ставит суперпользователь из каталога. Для этого процессу Daphne нужны `git` (доступ на чтение к репозиторию) и `node` с `node_modules` ядра, а также право записи в `modules/`.

| Переменная | Что делает |
|---|---|
| `SFERA_MODULES_REPO` | откуда брать модули: URL репозитория или имя remote (по умолчанию `origin` этого клона) |
| `SFERA_MODULES_FROM_REPO=0` | не обращаться к репозиторию: в каталоге только то, что уже лежит в `modules/` |
| `SFERA_MODULES_RESTART=none` | не перезапускать сервер после установки (перезапустите сами); по умолчанию процесс завершается и systemd (`Restart=always`) или автоперезагрузчик `runserver` поднимает его с модулем |
| `SFERA_MODULES_AUTOUPDATE=0` | не обновлять установленные модули автоматически (по умолчанию сервер сам ставит новую голову ветки в течение ~5 минут после пуша) |
| `SFERA_NODE` | путь к `node`, если его нет в PATH службы |

Состояние хранится в `modules/`: `.installed.json` (что и на каком коммите поставлено), `.bundles/` (собранные фронтенды), `.jobs/` (идущие и неудачные установки). На кластере установка идёт на одной ноде: повторите её на остальных или разверните их с тем же `.installed.json`.

```bash
node scripts/modules/fetch.mjs            # модули из modules/.installed.json и закреплённые в modules.lock.json
node scripts/modules/fetch.mjs --dev      # ветки модулей (attached) — чтобы коммитить в модуль
node scripts/modules/fetch.mjs --update   # закрепить текущие головы веток в modules.lock.json
```

`modules/` в `main` игнорируется: каждый модуль — это git worktree своей ветки.

**Выпуск новой версии модуля:** поднимите `version` в `module.json` и запушьте ветку `module/<id>` — на серверах в каталоге появится «Обновить».

**Новый модуль:** `git worktree add --orphan -b module/<id> modules/<id>`, затем `module.json`, `backend/`, `frontend/index.tsx` и CI из `scripts/modules/module-ci.yml`. Пока ветка не запушена, локальный модуль виден в каталоге как уже развёрнутый.

Деплой (`scripts/linux/start-common.sh`) восстанавливает модули из `modules/.installed.json`, ставит зависимости, мигрирует и собирает фронт ядра.

### Конференции без ограничения участников

Без медиасервера участники конференции соединяются напрямую — это подходит для небольших встреч. Для больших подключите [LiveKit](https://docs.livekit.io/home/self-hosting/deployment/) (открытый SFU, ставится на свой сервер) в настройках модуля или переменными `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`. Каждый участник отправляет один поток на сервер, получает только видимые плитки; ограничения на число участников в Сфере нет.

**Ядро без модулей обязано собираться и проходить проверки.** CI в `main` проверяет это отдельной job.

## Мониторинг и выбор при установке

Grafana и Prometheus получают конфигурацию из `django-server/monitoring/generated/`. Эту папку собирает `node scripts/modules/monitoring.mjs` из ядра (`django-server/monitoring`) и из `modules/<id>/monitoring` каждого развёрнутого модуля. Модуль, который не развёрнут, не даёт ни дашбордов, ни алертов.

Переменные деплоя (`/etc/sfera/deploy.env` или repo variables в GitHub):

| Переменная | Что делает |
|---|---|
| `SFERA_MODULES=servers,channels` | ставит только эти модули, остальные worktree удаляются; `none` — ядро без модулей |
| `SFERA_MONITORING_EXCLUDE=diary,core` | не ставит дашборды и алерты этих модулей (`core` — дашборды ядра) |
| `SFERA_MONITORING=0` | не поднимает Prometheus, Grafana и Alertmanager вовсе |
| `"monitoring": false` в `modules.lock.json` | постоянно исключает мониторинг модуля |

Данные модулей при этом не трогаются: исключённый из деплоя модуль просто не загружается, его таблицы остаются в базе.
